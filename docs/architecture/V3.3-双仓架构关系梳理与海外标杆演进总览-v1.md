### 1.2 核心判断：「本仓做交付工作平台，本体仓做企业本地部署交付物」是否准确？

**定性结论：大方向 80% 准确，但需补齐两处关键架构分层：**

1. **职责切分完全成立（Control Plane vs Semantic Runtime Plane）**
   - **`fde-workbench` 是我方 FDE 团队使用的「交付生产与商业治理母机」**：Electron 桌面端（`蔡工FDE-<version>-便携版`）只发给内部 FDE 工程师、项目负责人、审阅人与平台管理员使用，**绝不作为客户端软件分发给甲方企业员工安装**。
   - **`Fde-Ontology`（`ontology-service`）是可真正落入客户生产环境的「行业本体与受控动作运行时」**：承载客户业务对象（ObjectType）、外部数据库只读接地（Grounding Connectors）、血缘证据（Lineage）、受限 AST 规则（`logic_engine.py`）、受控写动作（Action dry-run / 异人审批 / 幂等回执）及只读/受控 MCP 工具面（`routers/mcp_tools.py`）。

2. **部署形态并非「唯一下沉本地」，而是按客户安全等级分三态交付（对齐 M6-D5）**
   - **形态 A（多租户云端 SaaS）**：中小客户无需本地机房，两套服务均部署于我方云端（双 PG 库隔离 + `org_id` 租户强隔离），仅连云端可达 API 或脱敏导入包。
   - **形态 B（客户专有私有化 On-Prem / 专有 VPC）**：制造业、政企、金融等高敏客户，将 **`ontology-service` 容器栈 + 本地自托管 LLM + 内网只读 SQL / 受控写 Webhook 连接器** 部署在客户内网机房，原始业务数据 100% 不出客户内网。
   - **形态 C（混合云 + 本地连接器/边缘回执）**：云端作战室统筹交付，客户内网仅跑受控 Runtime Pod 与连接器，单向回传脱敏摘要与指针哈希。

3. **企业最终拿到的完整交付物是「四件套组合」，而非裸跑一个后端容器**
   - ① **运行时引擎**：`ontology-service` 容器化服务与 MCP/REST 语义接口；
   - ② **行业本体资产包**：声明式九要素模板实例（`OntologyTemplateBundle`）及开放标准导出件（JSON-LD / OWL-Lite，零厂商锁定）；
   - ③ **受控业务自动化流**：绑定钉死 `ontology_version_id` 快照的追溯/质检/工单闭环配方；
   - ④ **防伪合规验收包**：门禁 G1–G9 签发的离线可验签 `Frozen Evidence Pack`（HTML/PDF + SHA-256 清单）。

## 二、对标海外顶尖实践：当前架构体检全景

参考海外最成熟的企业本体与 FDE 工程体系——**Palantir（Foundry Ontology + Apollo 跨环境交付引擎 + OSDK）**、**RelationalAI（语义协处理器）**、**dbt Semantic Layer / Cube（声明式语义层即代码）**、**Google CEL（非图灵完备安全规则语言）**，以及硅谷新一代 **FDEOps 平台（Tandem、Auctor、Nixo、Temporal）**：

### 2.1 当前架构已经踩对的 4 个「硅谷级高分设计」

1. **Kinetic + Dynamic 运营级本体，而非静态知识图谱（对齐 Palantir Foundry）**
   没有掉进 `Neo4j + 裸 Text2SQL` 的泥潭，而是把 **Semantic（对象/关系）+ Kinetic（连接器接地映射）+ Dynamic（AST Logic + 带审批幂等的 Action + D26 服务端注入七元组 MCP）** 固化在同一不可变 `OntologyVersion.snapshot`（`fingerprints.py` 规范化 JSON SHA-256）中。Agent 调用的是钉死版本的业务原语，而非裸拼 SQL。
2. **极度克制的基础设施选型（PG16 单栈起步）**
   私有化进客户机房时，每增加 Neo4j / Kafka / NATS / Kubernetes Operator 等重组件，现场运维成本翻倍。PG16 单底座在百万级实体以内兼具 ACID 与极低运维门槛。
3. **Zero-Copy 指针化合规纪律（`source_uri` + `sha256`）**
   原始客户敏感明细留驻本地源库或真相层，跨面只传指针与摘要，天然契合金融/制造数据不出域要求。
4. **AST 白名单零任意代码执行（`logic_engine.py`）**
   从根源阻断 Prompt Injection 演变为 RCE 或越权写库。

### 2.2 穿透源码识别出的 5 个结构性隐患（2→N 家客户规模化瓶颈）

| 编号 | 隐患领域 | 源码取证锚点 | 真实客户现场痛点（为什么会卡脖子） |
| :--- | :--- | :--- | :--- |
| **隐患 1** | **私有化场景下的「控制面断联」与商业机密暴露两难** | `Fde-Ontology/.../context.py:160-183`（强制对称 `X-API-Key` + `X-FDE-Context` HMAC 300s 窗）；`fde-workbench` 含 `commercial`/`diagnostics`/`dispatch` | 若客户内网只部署 `ontology-service`，断联云端 Workbench 后客户主管连**本地查看待批 Action、点击异人审批放行**的合法入口都没有；若把整套 `fde-workbench` 搬进客户机房，我方内部**五席位分账、报价缓冲系数、渠道线索池、派单算法**等核心商业机密代码与表结构将全部暴露在客户主机上。 |
| **隐患 2** | **双本体账本分裂（Dual-Ontology Split-Brain）** | `fde-workbench/.../ontology/models.py:120-192`（`OntologyTerm`/`OntologyChangeSet`）vs `ontology-service/models/working_set.py` | 售前/调研期在 Workbench 维护一套术语与关系变更集，实施期在 `ontology-service` 又维护一套对象与关系变更集；缺少单向晋升（Promote）与权威切换机制，驻场极易出现双边改名漂移。 |
| **隐患 3** | **单活跃 ChangeSet 全局锁 + 全量大 JSONB 阻碍多人并行建模** | `ontology_mock.py:92`（`_locked_by_ontology`）；`routers/change_sets.py`（单本体单锁窗口） | 中大型交付现场往往「数据工程师 A 调 ERP 接地映射，FDE B 调客诉 Action 参数」并行作业；全局单锁迫使串行排队，且 UI/REST 逐条点选建模效率远低于声明式代码（YAML + Git 分支合并）。 |
| **隐患 4** | **`logic_engine.py` 二进制浮点精度坑与单层标量表达力见底** | `Fde-Ontology/.../logic_engine.py:42-50, 166-175, 179-259` | ① `number` 直接用 Python `float`（如 `0.1 + 0.2 != 0.3`），算财务金额、良率阈值、工艺公差会出现致命边界误判；② `_walk` 仅放行单层 `input.<field>` 与 `abs/min/max/len/round`，不支持 `in` 枚举判定、不支持关联集合聚合（`sum/avg/any/all`）、不支持日期窗口差值，扛不住真实制造业 ERP/MES 规则；③ `run_expression`（297–317 行）每次执行重复解析两遍 AST。 |
| **隐患 5** | **793 行手写 `ontology_mock.py` 语义漂移风险** | `fde-wt-v33m4/.../ontology_mock.py:1-793`（如 139 行 `repr(snapshot)` 算 ETag vs 真机规范化 JSON SHA-256） | Workbench 单测依赖手写内存 `MockOntologyAdapter` 替身，而真机是 FastAPI + PG16 + `ontology-api-spec.yaml`；若无自动化双向契约一致性门禁（Golden Parity Gate），极易出现「Mock 全绿、真机联调 409/422 炸裂」。 |

| 改进单编号 | 解决的核心隐患 | 对标海外标杆 | 建议落地阶段 | 核心交付物摘要 |
| :--- | :--- | :--- | :--- | :--- |
| **改进单 1（边界解耦）** | 隐患 1（私有化断联 & 机密外泄） | **Palantir Apollo + Auctor Local Portal** | M6-WP5 / V3.4 先行 | 划清 **Cloud War-Room（仅我方持有）** 与 **Customer Runtime Pod（可独立存活交付包）** 物理红线；为 `ontology-service` 增配 Ed25519 非对称签发策略包 + 可选 `Local Governance Micro-Console`（仅含只读拓扑/血缘 + Action 异人审批 + 离线证据导出），**严禁 `commercial/diagnostics/dispatch` 进客户机房**。 |
| **改进单 2（规则引擎加固）** | 隐患 4（`float` 精度坑 & 规则表达力不足） | **Google CEL（非图灵完备强类型表达式）** | M5 尾批 / M6-WP1 | `logic_engine.py` 升级 `v2`：数值运算全面切换 **`Decimal` 十进制精确算术**；单次 AST 编译缓存；在保持 100% 必终止与零注入前提下，扩充 `in/not in`、受限集合归约宏（`sum_by/avg_by/any_of/all_of`，硬封顶元素数 `MAX_COLLECTION_ITEMS = 1000`）、ISO 日期差值 `days_between` 与 `coalesce`。 |
| **改进单 3（双仓契约焊死）** | 隐患 5（793 行手写 Mock 漂移） | **Pact / OpenAPI Schema + Golden Trace 双跑门禁** | M5 / CI 常驻 | 建立以 `ontology-api-spec.yaml` 为单一真身的 **三向一致性门禁**：① OpenAPI Schema 响应校验；② 同一套 Golden Scenario 状态机脚本同时驱动 FastAPI `TestClient` 与 Flask `MockOntologyAdapter` 比对状态码/错误码/ETag/幂等语义；③ 消除 `build_context_header` 与 ETag 算法分叉。 |

## 四、实施优先级建议（供拍板参考）

1. **第一顺位（立即可做、零架构破坏、防线上事故）**：**改进单 3（双仓契约一致性门禁）** + **改进单 2 Phase A（`logic_engine.py` Decimal 精度修复与集合/枚举原语扩充）**——可在不改任何数据库表结构的前提下，直接把制造业试点与财务数值计算的底盘焊牢。
2. **第二顺位（随 M6-WP2 模板化顺势落地）**：**改进单 4（Ontology-as-Code 声明式规范与 Glossary 单向晋升）**——直接作为 M6-D1 `OntologyTemplateBundle v0.1` 的工程实现规格，避免模板包退化成无法 Diff 的万行死 JSON。
3. **第三顺位（首家纯内网私有化客户进场前必做）**：**改进单 1（云端作战室 vs 客户本地 Runtime Pod 独立存活边界）**——在真正往客户内网机房交付镜像前，切干净打包制品与本地最小审批环，守住平台商业分账与多客户数据资产红线。
