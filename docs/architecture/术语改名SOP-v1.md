# 术语改名 SOP（v1，2026-11-06）

> 来源：v3-迁移进度对照报告 §五-4 / §六 #7（「改业务名先改术语表」此前无 SOP 文档；代码消费面已由 T-I1 影响分析成立）。**文档强制先行**；代码强制（服务端拦截未先改术语表的改名）挂后续评估——T-O3 双轨裁决维持，先在本文件补设计再动代码。

## 0. 为什么改名必须先过术语表

引用合同 = **名字域纽带**（`server/src/fde_api/ontology/service.py` 模块 docstring）：本体表与业务对象之间没有 term_id 外键，「同项目一个名字至多一个概念」（UNIQUE(project, term) / UNIQUE(project, alias)）使**名字精确等价概念引用**——`subject.name` 精确命中生效名字域即引用该概念，子串不算命中（T-I1 影响分析即按此合同实现）。

直接改业务对象名而不动术语表的两种事故形态：新名字撞上**另一个概念**的生效名（引用静默重挂到错误概念）；或脱离原概念名字域（影响分析/血缘/合并链对该对象全部失配）。

## 1. 触发条件

- 要修改某业务对象名（调研对象 `subject.name`、表单名等），且该名字已被术语表登记（或按口径应当登记）；
- 或业务命名口径变化，涉及术语规范名 / 别名调整。

## 2. 流程（四步，顺序不可换）

1. **先查影响面**：GET `/api/v1/projects/{id}/ontology/terms/{term_id}/impact`（桌面：项目 tab「术语表」→ 行内「影响分析」，随待办池清欠轮接线）。三面清单：`subjects`（精确名命中，带 `matched_via`/`matched_term_id` 溯源）、`links`（端点邻接边）、`forms`（表单 + 现行修订状态）。对**并入行**查询 = 查其存活概念的影响面（`resolved.canonical_term_id` 给出解析目标）。
2. **术语表改名走变更集**（全系统唯一 definition 写路径；confirmed 定义无原地编辑路径是设计）：change-set propose `rename`（物化语义＝旧行 superseded + 新行 confirmed + 原名转别名，T-O3）→ 拍板人 ≠ 提交人 → confirm（base 指纹复核，全成全败）。桌面入口：术语表「变更集评审」面板。
3. **按影响清单改引用面**：对第 1 步三面清单逐项走既有对象编辑通道改名；同名让位与合并候选语义沿用 T-O4（文件 vs 项目既有 active 同名同类型＝让位，不静默新建合成键对象）。
4. **别名不清理**：改名留下的历史别名是血缘溯源凭证（`matched_via`），合并链一跳化靠它；不因「看着冗余」而删除。

## 3. 边界与反例

- **改名 ≠ 合并**：两个概念并为一个走 `merge_terms`（T-O1 原语 / change-set 物化），不走 rename。
- **不要绕过变更集直改 DB**：服务层对 confirmed 定义无编辑路径是防旁路设计；`captured_from` 仅服务层原语可写、HTTP 拒收。
- **AI 候选同样走此 SOP**：AI 提案落 change-set（`captured_from` 可溯源），人工拍板后才执行第 3 步；桌面不提供直接改术语的入口。
- **关系类型 / 对象类型不是术语**：kind=link_type / subject_type 的 label 与码不在名字域纽带内；注册类型走 retire + 重建（T-O2），不走术语 rename。

## 4. 代码强制挂账

「未先改术语表就改业务名」目前**无服务端硬拦截**（靠本 SOP + 评审纪律）。如需强制（对象改名端点前置 impact 非空检查或同名术语占用检查），须先在本文件 §4 补设计（含对导入 T-O4 让位语义的影响评估）再立项动代码。
