## 二、逐条评估

### 2.1 B#3「AI 审查不执行被审代码」——暂无可断言对象

**红线要求**：AI 审查/评审的输入只能是 diff/文本快照；不得检出、不运行被审交付的代码、测试、配置或 hooks。

**实测事实**：

- 仓库工作流仅 `.github/workflows/ci.yml` 一个；`grep -rn "claude|copilot|ai-review|llm" .github/workflows/` **零命中**。
- 即：**AI 审查面尚未上线**，不存在「审查时执行了被审代码」这一可观测行为。

**为何不能补守卫**：

- 无对象可断言——`ci.yml` 里没有 AI 审查步骤，断言无从写起。
- 未来若上线 AI 审查 job，判据应是「该 job 的 `run:` 步骤不出现 `checkout` 后的执行类命令」，
  即断言 **workflow YAML 本身**（不检出被审代码、不执行其测试），而非断言代码内容。
- **落地时机**：AI 审查 job 首次进入 `ci.yml` 的那个 PR，必须同 PR 补上该断言（红线原文已写明这个条件）。

**风险提示**：该红线在 AI 审查面上线前**处于「无对象可守」状态**。
若此时删除，唯一代价是**丢失一个未来的实施约束**——但因为原文自带「未来…时加 CI 断言」的条件，
删除后若上线 AI 审查面，容易**忘记补这条约束**。

### 2.2 B#35「第三方材料只译抽象、不复制结构化表达」——部分可断言

**红线五个子项的可断言性**：

| 子项 | 内容 | 可断言性 | 判据 |
| --- | --- | --- | --- |
| ① | 抽象概念可用，思想/方法/维度/判据结构可借鉴并独立重写 | ❌ 无法断言 | 「是否等价」是语义判断 |
| ② | 无 LICENSE/许可链未闭合仓库的**结构化表达**禁写入本仓 | ⚠️ **部分** | 可断言「某 PR 引用了无 LICENSE 的第三方仓库」；但「是否等价复现（改数字/换措辞/重排）」无法机械判定 |
| ③ | 独立重写须声明「来源对照表」 | ✅ **可断言** | 引用第三方材料的 PR 必须在正文含来源对照声明——可用**必需章节标记**断言（如固定小节标题） |
| ④ | 时效判据：登记确切版本/许可/出处/**快照日期**；>30 天停更快照失效重核 | ⚠️ **部分** | 「快照日期」字段可断言存在且格式合法；「是否已停更 30 天」需外部数据源，CI 内不可得 |
| ⑤ | 许可混置须逐件核（`fde-skills` 的 `legacy/` MIT／Apache-2.0 vs 顶层 AGPL-3.0-only） | ⚠️ **部分** | 可断言「引用 `fde-skills` 的产物旁带许可声明」；但「逐件核」的执行完整性无法断言 |

**可行的机械守卫（建议候选）**：

1. **来源对照表存在性守卫**（子项 ③ 的可断言子集）
   - 判据：凡在 PR 描述或 `docs/architecture/**` 新文档中出现「借鉴 / 参考 / 来源 / 上游 / 开源项目」等第三方引用标记，
     同文件必须含固定小节（如 `## 来源对照`）且列出「来源仓库 / 版本或 commit / 许可 / 快照日期 / 我方独立重写说明」四要素。
   - 断言形态：`docs/architecture/` 与 `docs/audit/` 下新文档扫描 + 必需字段正则。
   - **误伤风险**：中——需精心构造关键词集，避免把「本项目内部借鉴」误判为第三方引用。

2. **许可声明存在性守卫**（子项 ⑤ 的可断言子集）
   - 判据：产物目录中出现第三方项目名（如 `fde-skills` / `fde-gym` / `agent-autoloop` / `agnes-harness` / `giip-fde-agent`）时，
     同目录必须有 `LICENSE-NOTICE` 或等价许可说明文件。

**为何不建议做「等价复现」检测**：

- 版权保护的是**编排与结构化表达**，不是数字。检测「改数字/换措辞/重排的等价复现」需要语义比对，
  工程量等同做一个代码相似度检测器，**误报率会高到不可用**，反而制造假红、稀释守卫可信度。

### 2.3 #129/#131「口径数字引用前现测」——高度可断言，建议立即补（P0）

**红线要求**（含六项测量配方）：文档口径一律**重测不承袭**；表数=`__tablename__` 去重 grep；路由=装饰器计数 grep；
api_catalog ENTRIES=awk 数 `("` 行；迁移头=revision 集减 down_revision 集；mypy=基线行数且只认 `scripts/check-python-types.py`；
pytest/vitest 只认 CI 实测轮次。改动任一口径值时**对全文同模式终扫**。

**为何可断言**：

- **配方已明确**——六个口径各自有确定的计算方法，等于可执行规范。
- **锚点稳定**——「当前状态」节内**第一条以 `- **` 开头的轮次 bullet** 唯一含 pytest/vitest/mypy/api_catalog/表数 五项口径（实测该节仅 1 条此类 bullet，命中稳定）。
- **有现成范式可仿**——`scripts/check-python-types.py`（128 行）已是「计数法 + 基线文件 + CI 接线 + `--update` 显式收紧」的成熟模式，口径守卫应照此形态写。

**⚠️ 实测发现的历史漂移（本评估撰写时，旧快照 825 → 已被 #151 自愈）**：

| 口径 | 评估撰写时 AGENTS.md 记载 | 实测值（2026-11-06） | 现状 |
| --- | --- | --- | --- |
| pytest | 1985 收集＝1979 passed＋6 skipped | 未在本机跑（需 PostgreSQL 测试库） | 待核 |
| **vitest** | **825**（旧快照） | **828**（PR#147 新增 3 例官网令牌守卫） | ✅ **#151 回滚轮重核已同步为 828，漂移已自愈** |
| mypy | 279 | 未本机跑（依赖 `check-python-types.py` 基线） | 待核 |
| api_catalog ENTRIES | 94 | 94 | ✅ 一致 |
| 表数 | 105 | 105 | ✅ 一致 |
| 迁移头 | 36 | 36 | ✅ 一致 |

**修订注（v1.1）**：本表最初记录的是「文档 vitest 825 / 实测 828 → 已漂移」，用以证明红线 3 的「活值残留」真实发生。
随后并行会话 #151（`c492871`，V3 回滚轮落定重核轮）在执行「口径数字引用前现测」配方时，
已把 AGENTS.md 现役段 vitest 口径同步为 **828/828**——**历史漂移已被人用配方自愈**。

但同一配方扫描发现：「当前状态」节历史 bullet 内仍散布 **42 处口径值**（如 `pytest 1986` / `vitest 825` / `mypy 279` / `api_catalog 94`），
这些是**各轮次的口径快照**（合法保留），**不是现役口径**。因此：

- 本评估 §2.3 原「锚点＝首条 `- **` 轮次 bullet 唯一含五项口径」的判断**需精确化**——
  历史上「当前状态」节有 42 处口径值散布，**锚点必须限定为「首条 `- **` 轮次 bullet」（即最新轮次），不能全节扫描**，否则会把历史轮次的口径值误当现役口径、制造假红。
- 守卫设计已照此实现：只取「当前状态」节内**第一条**以 `- **` 开头的轮次 bullet 作为现役口径段，**不扫后续 bullet**。

**P0 守卫的真实价值**（修订后）：
1. 防未来再漂移（#151 已证明人用配方能自愈，但守卫把「自愈」从手工动作变成 CI 自动断言）；
2. 防「锚点误扩」——守卫自身必须只锚定首条轮次 bullet，避免把 42 处历史口径值当现役口径误报。

**建议的守卫形态**（照搬 `check-python-types.py` 范式）：

```
scripts/check-doc-counts.py
  ├─ 只认「当前状态」节首条轮次 bullet 为现役口径段（锚点唯一）
  ├─ 对四类可本机复算的口径做实测比对：
  │    表数      ← grep __tablename__ 去重
  │    迁移头    ← revision 集减 down_revision 集
  │    api_catalog ENTRIES ← awk 数 (" 行
  │    vitest    ← 统计 desktop 测试文件中的用例数（静态计数，不跑测试）
  ├─ 口径不符 → 报红并指出「文档写 X / 实测 Y」
  └─ --update 模式：显式重写现役段口径值（须在干净树执行）
```

**pytest 与 mypy 为何不纳入本守卫**：

- pytest 需隔离 PostgreSQL 测试库，CI 里是独立 job（`server-tests`），与文档校验 job 不同环境，
  难以在同一守卫内复算；且其口径须「只认 CI 实测轮次」——天然属于 CI 产物，不适合本地脚本断言。
- mypy 已有 `scripts/check-python-types.py` 独占（红线 3 明写「只认」），不宜两处各算一套。

**因此建议**：本守卫覆盖 **表数 / 迁移头 / api_catalog / vitest** 四项（均为**纯静态可复算**，零外部依赖、零数据库、秒级完成）；
pytest 与 mypy 继续由既有机制（CI 实测 + `check-python-types.py`）负责，并在守卫注释中写明这层分工。

**vitest 计数口径已验证（2026-11-06 实测）**——原「静态计数」方案**不可行**，改用 `vitest list`：

| 计数方式 | 结果 | 与实际跑（828 / 68 文件）是否一致 | 耗时 |
| --- | --- | --- | --- |
| 正则静态扫 `it(` / `test(` 调用 | **680** | ❌ 差 148（`it.each` 展开、helper 生成用例等无法静态数出） | <1s |
| `npx vitest list --run` | **828 用例 / 68 文件** | ✅ **完全一致** | 约 36s |

**结论与方案调整**：

- 静态文本扫描**不可用作口径判据**（偏差 148，误报必然）。
- 改用 `vitest list --run` 作为唯一判据——它是 vitest 自身的清单 API，**权威且零歧义**。
- **副作用**：该命令需加载测试模块，因此守卫**不能放进纯文档校验 job**，须接入 `desktop` job
  （已有 node_modules 与 vitest 配置），或作为独立 job 运行（需 `npm ci`，成本约 2–3 分钟）。
- `vitest list` 只读不执行测试、不需数据库与浏览器环境——实测 36 秒完成，**不构成 CI 负担**。

**四项口径的最终可断言形态**：

| 口径 | 判据方式 | 独立性 |
| --- | --- | --- |
| 表数 | `grep __tablename__` 去重（纯文本） | 零依赖，可进任何 job |
| 迁移头 | revision 集减 down_revision 集（纯文本解析） | 零依赖 |
| api_catalog ENTRIES | `awk` 数 `("` 行（纯文本） | 零依赖 |
| vitest 用例数 | `vitest list --run`（需 node_modules） | 需 desktop job |

**实施建议**：拆成两段——`scripts/check-doc-counts.py --static` 覆盖前三项（任何 job 可跑），
`--with-vitest` 追加第四项（desktop job 跑）。

## 四、给决策者的两点提醒

1. **删红线 ≠ 失去防护，但也 ≠ 无成本**。三条红线目前**都没有自动化守卫**，
   保护力完全依赖人读 AGENTS.md。删掉后：
   - B#3 的条件约束（未来上线 AI 审查面时补断言）容易**被遗忘**；
   - B#35 的许可边界在无守卫情况下，风险敞口**由人工评审承担**；
   - #129/#131 的口径纪律**靠人记不可持续**——本评估撰写时（旧快照 825）实测已漂移，
     后续被并行会话 #151 用配方自愈为 828；「42 处历史口径值散布在『当前状态』节」的新发现
     进一步证明**无守卫时口径易串位、且难以全节终扫**，守卫须精确定位首条轮次 bullet。

2. **建议不要以「补守卫」为条件保留红线**，而应把红线**降级为「待自动化的纪律条目」**并挂上实施排期——
   否则会出现「等守卫写好再谈删除」的死锁：守卫需要设计时间，红线删除是当下决策。
