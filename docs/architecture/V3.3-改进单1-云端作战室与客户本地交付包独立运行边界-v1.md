## 1. 问题诊断（Why）

当前双仓契约规定 `ontology-service` 所有业务端点均依赖 `fde-workbench` 实时签发的 `X-API-Key` + `X-FDE-Context`（对称 `ONTOLOGY_CONTEXT_HMAC_SECRET` + 300s 时间窗，`context.py:29, 160-183`），且规定「Workbench 是唯一面向人的入口」。这在客户专有私有化（On-Prem / Air-gapped VPC）场景下引发结构性两难：

1. **若客户机房仅部署 `ontology-service`**：断联云端 Workbench 后，客户内网系统/本地 Agent 触发高风险 `ActionRequest`（`proposed` 态）时，客户现场主管**没有任何合法本地界面或鉴权通道完成「异人审批（Approve / Reject）」**，生产闭环中断。
2. **若把整套 `fde-workbench` 镜像一并部署进客户机房**：`fde-workbench` 内含我方核心商业机密与多客户运营逻辑——五席位商业分账（`fde_api/commercial/` 19 张表）、报价缓冲系数（`quote_service.py`）、公网获客诊断线索池（`fde_api/diagnostics/`）、FDE 派单撮合算法（`fde_api/dispatch/`）及跨项目经验库（`seeds/lessons.json`）。整仓进客户机房等于将平台底牌交由客户宿主机 root 管理员裸读。

## 2. 核心架构原则：双平面硬切分（Cloud War-Room vs Customer Runtime Pod）

| 维度 | 云端军团作战室（Cloud War-Room = `fde-workbench`） | 客户本地交付包（Customer Runtime Pod = `Fde-Ontology` 交付制品） |
| :--- | :--- | :--- |
| **部署归属** | **100% 留驻我方云端 / FDE 自持便携端**，严禁打入客户私有化交付镜像 | 部署于客户专有 VPC / 本地机房（或 SaaS 租户隔离命名空间） |
| **核心职责** | 立项报价、访谈抽取（Discovery）、术语收集、模板研发、FDE 派单、G1–G9 门禁封包、商业分账结算 | 承载已签名本体版本（`OntologyVersion`）、本地连接器接地、AST Logic 计算、Action 审批执行、MCP 工具服务 |
| **面向人群** | 我方 FDE 工程师、项目经理、平台审阅人、管理层 | 客户侧业务系统、客户侧授权 Agent、客户现场业务审批主管 |
| **断网自治能力** | 离线可编辑方案，联网同步 | **100% 断网自治（Air-gap Survivable）**：凭已导入的签名发布包独立完成查询、推理、本地异人审批与审计落盘 |
| **严禁越界红线** | 严禁落盘客户生产库明文行数据与连接器密钥明文 | **严禁包含 `commercial` / `diagnostics` / `dispatch` / 跨客户模板源码** |

## 3. 具体技术改造方案（How）

### 3.1 鉴权双模化：保留云端 HMAC 网关模，新增本地独立存活模（Standalone OIDC/JWT + 公钥验签）

修改 `ontology-service/src/ontology_service/context.py` 与 `config.py`，引入显式部署模式枚举 `ONTOLOGY_DEPLOYMENT_MODE`：

1. **`gateway` 模式（默认，兼容 M1–M4 零回归）**：
   - 保持现有 `X-API-Key` + 对称 HMAC `X-FDE-Context` + `SeenNonce`（`context.py:103-183`）一字不变，供云端 SaaS 与混合云受控网关使用。
2. **`standalone_pod` 模式（新增，专供客户内网私有化交付）**：
   - **人机本地鉴权**：支持配置客户内网标准 OIDC / 本地轻量签发器（Ed25519 / RS256 公钥验签 `ONTOLOGY_LOCAL_AUTH_JWKS_PATH`），从已验签 JWT 提取 `sub -> actor_id`、`org_id`（锁死为本客户固定单租户常量 `ONTOLOGY_LOCKED_ORG_ID`）、`roles`；**由 `ontology-service` 本地中间件构造不可伪造的 `FdeContext`**，依然 100% 强制执行 D26 `reject_injected_context`（禁止客户端 Body/Query 自带七元组）。
   - **发布包离线验签（Signed Release Bundle）**：云端 Workbench 编译好本体版本后，导出带 **Ed25519 私钥签名** 的 `.ontpkg` 发布包（内含规范化 `OntologyVersion.snapshot` + `snapshot_sha256` + 授权 `org_id` + 签名头）；客户机房 `ontology-service` 仅内置我方 **Ed25519 公钥**，导入时验签通过方可激活为不可变版本，杜绝现场私自篡改未审本体结构。

### 3.2 极薄「客户本地治理微台（Local Ops Micro-Console）」

不在客户机房部署 Electron / 完整 Workbench，而是在 `Fde-Ontology` 仓新增可选静态单页包 `local-ops-ui/`（可通过 `ONTOLOGY_LOCAL_CONSOLE_ENABLED=false` 默认关闭，私有化交付按需开启），**功能范围严格锁死为 4 个最小闭环视图**：

1. **当前生效本体拓扑只读视图**：展示当前激活 `ontology_version_id`、对象/属性/关系字典与 JSON-LD/OWL-Lite 开放导出按钮。
2. **连接器健康与配额状态页**：展示只读 SQL / 受控写 Webhook 连接器的连通性、限流计数（429/504）与 `reconciliation_required` 待核对告警（零密钥明文回显）。
3. **Action 异人审批工作台（核心刚需）**：列出 `status = proposed` 的高风险动作请求，展示 `dry_run` 影响预览、触发血缘（`evidence_chain`），供客户现场有权限的业务主管点击「批准执行 / 驳回」（后端硬校验 `approver_id != proposer_id` 异人审批铁律）。
4. **离线审计回执导出**：一键导出段时间内的 `ActionRequest` 执行账本与 `audit_events` 签名摘要包（JSONL + SHA-256），供 FDE 驻场复盘或回传云端 Workbench 挂接 G8/G9 门禁证据（只传指针与指纹，不传客户敏感载荷）。

### 3.3 双仓跨网异步对账（Outbox & Air-gap Sync）

- **联网/混合云态**：Workbench 侧推进「项目版本绑定」「门禁证据固化」时，统一经 Workbench `OutboxEvent`（携带确定性 `X-Idempotency-Key`）投递，消除双 PG 库同步 HTTP 抖动半态。
- **纯内网离线态**：通过 `fde-cli bundle export --sign`（云端出包）与 `ontology-cli audit export --verify`（现场回执包）两条离线文件管道闭环，与 `AGENTS.md`「门禁只存 `source_uri` + `sha256`」红线严丝合缝。
