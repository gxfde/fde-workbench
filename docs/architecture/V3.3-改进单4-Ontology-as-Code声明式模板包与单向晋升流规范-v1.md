## 1. 现状痛点诊断（Why）

1. **大 JSON 快照无法做人类可读 Code Review 与跨厂参数化复用**：
   - 若 `OntologyTemplateBundle` 退化成一个几千行的扁平 JSON 快照，FDE 为「工厂 B」微调一个不良率阈值（`0.03 -> 0.025`）或改一个 ERP 表字段映射，Git Diff 会淹没在无序 JSON 噪音中，且极易破坏 M6-D1 要求的「反注水 `out_of_box_rate`（固化内核 vs 可变参数物理分离）」核算。
2. **单活跃 ChangeSet 全局排他锁阻塞多人驻场并行**：
   - 真实项目交付时，数据工程师调 `connectors/mappings`（Kinetic 层），业务顾问调 `actions/logic`（Dynamic 层）；粗粒度全本体单锁迫使团队串行等待。
3. **Workbench `Glossary` 与 `ontology-service` 双账本分裂（Split-Brain）**：
   - Workbench `fde_api/ontology/` 维护项目术语表，而 `ontology-service` 维护运营对象类型；若两边均可独立增删改同一概念，调研期产物与运行期模型必然脱节。同时 `fde_api/ontology/service.py` 已受 2102 行热点预算死锁保护，**绝不可往旧模块硬塞新代码**。

## 2. 核心设计三支柱

### 支柱一：`Ontology-as-Code` 多文件声明式目录结构（完美对齐 §12 九要素与 M6-D1）

在 Workbench 新增独立包 `server/src/fde_api/ontology_templates/`（零触碰 `ontology/service.py` 行数预算），将行业本体模板定义为 **Git 友好的分目录 YAML 包（`.ontbundle/`）**，物理隔离 **「不可变行业内核（Kernel）」** 与 **「客户现场可变槽位（Overlay / Params）」**：

```text
templates/manufacturing-quality-traceability-v1/
├── bundle.yaml                     # 要素①⑨: 元数据、适用/非目标范围、兼容版本、九要素文件 SHA-256 清单
├── params.schema.yaml              # 要素⑨: 客户现场可变参数强类型 Schema（阈值、枚举、表别名槽位）
├── params.default.yaml             # 默认参数值（工厂 A/B 实例化时仅覆盖 customer-params.yaml！）
├── glossary/
│   └── terms.yaml                  # 要素③: 标准业务术语词典（含信通院 WG15 可选对齐槽位）
├── kernel/                         # 要素②⑥: 行业固化本体内核（修改此处会计入内核变更，扣减 out_of_box_rate）
│   ├── objects.yaml                # 13 类标准对象（ProductBatch, SupplierBatch, Complaint, CorrectiveAction...）
│   ├── relations.yaml              # 12 条标准有向语义关系与基数约束
│   ├── logic_rules.yaml            # CEL/AST 声明式规则（引用 {{ param.max_defect_rate }} 参数槽位，非硬编码数字！）
│   └── actions.yaml                # 受控动作契约（dry_run 规则、异人审批要求、幂等策略）
├── grounding/
│   └── mapping_guide.yaml          # 要素⑤: 逻辑对象 ← 源系统视图映射契约模板（连接器槽位悬空待现场绑定）
├── recipes/
│   └── agent_workflows.yaml        # 要素⑦: 最小 Agent 七步追溯配方与 MCP 工具白名单绑定
├── acceptance/
│   └── gate_checklist.yaml         # 要素⑧: G1–G9 门禁证据清单模板
└── fixtures/
    └── synthetic_samples.jsonl     # 要素④: 强制带 "data_authenticity": "SYNTHETIC_PILOT" 的回归测试脏样本（含 5 类故障）
```

**关键机制：参数插槽编译（Slot Parameterization）**
- `logic_rules.yaml` 中写 `input.defect_rate > param.critical_defect_threshold`，编译实例化时由编译器校验 `customer-params.yaml` 的类型并注入静态常量 AST 节点（严禁拼字符串注入表达式！）。
- **收益**：第二家客户（工厂 B）只需提供 30 行 `customer-params.yaml` + `grounding-bindings.yaml`，内核文件 SHA-256 保持 100% 零改动，系统可**按字节哈希精确算出真实的反注水 `out_of_box_rate`**！

### 支柱二：从「全本体粗锁」演进为「对象级内容寻址三路合并（Object-Level Three-Way Merge）」

借鉴 Git 与 Palantir Ontology Branching，解除多人并行瓶颈，同时**不引入复杂图数据库**：

1. **草稿期并发无锁（Optimistic Concurrent Drafts）**：
   - 允许同一 `ontology_id` 同时存在多个 `draft` 态 ChangeSet，每个 ChangeSet 记录创建时的 `base_version_id`（基准快照祖先）。
2. **基于元素指纹（Element-Level Merkle Hash）的提交期冲突检测**：
   - 在 `ontology-service/fingerprints.py` 为快照内每个独立命名实体单独计算稳定哈希：
     - `object:<api_name>`、`relation:<api_name>`、`mapping:<object_api_name>`、`logic:<rule_id>`、`action:<action_id>`。
   - 当 ChangeSet B 请求锁窗/合并，而期间 ChangeSet A 已经发布了新版本 `V_new` 时，服务端对比 `Base -> A` 与 `Base -> B` 的修改集合 $\Delta_A, \Delta_B$：
     - **若 $\Delta_A \cap \Delta_B = \varnothing$**（例如 A 只改了 `mapping:ProductBatch`，B 只改了 `action:CreateCorrectiveAction`）：**自动无损快进重放（Auto-Rebase），零人工阻塞**！
     - **若 $\Delta_A \cap \Delta_B \neq \varnothing$**（双方改了同一个对象或同一条规则）：精准返回 `409 change_set_element_conflict` 并列出冲突实体键列表 `conflicting_elements: ["object:ProductBatch"]`，交由人工裁决。
   - **发布锁收敛为瞬时原子事务**：仅在最终 `publish` 写入 `OntologyVersion` 的毫秒级事务内对 `ontologies` 主行加 `SELECT ... FOR UPDATE` 行锁，彻底消灭长达数小时的人工审阅期全库死锁！

### 支柱三：消除双本体分裂 —— Workbench `Glossary` → `ontology-service` 单向晋升协议（One-Way Promotion）

明确划定两套模型的生命周期边界，遵循**「售前调研词条归 Workbench，正式运行模型归 Ontology Engine，晋升后单向投影不回流双写」**：

```
[阶段 1: 访谈与调研期]                 [阶段 2: 晋升闸 (Promote)]              [阶段 3: 建模与生产运行期]
Workbench: Discovery / Glossary  ───► POST /integrations/ontology/promote ───► ontology-service: ObjectType / RelationType
(自由词条收集、同义词归并、A/B/C 核验)     (人工勾选题名确认，生成初始 ChangeSet)      (唯一权威真身 SSOT)
        │                                                                            │
        └─────────── 晋升后词条状态置为 promoted_readonly ◄── 只读投影 `external_ref` ──┘
                     (Workbench 侧禁改核心语义，仅展示绑定的 ontology_version 锚点)
```

1. **数据契约最小改动**：
   - 不改 `ontology/service.py` 主逻辑；在 `server/src/fde_api/integrations/`（或新包 `ontology_templates/`）提供晋升编排函数 `promote_glossary_terms_to_changeset(project_id, term_ids, target_ontology_id)`。
   - 已晋升词条记录远端权威指针 `(ontology_id, canonical_api_name, promoted_at_version)`；后续改名或增删属性一律走 `ontology-service` ChangeSet，彻底根除「双边各自改名」导致的语义脑裂。

### 支柱四：本地离线 CLI 与合成脏数据预检闸（`ontology-bundle` 工具链）

供 FDE 在驻场或使用宿主编码通道（`zcode`）时高速迭代：
1. **`ontology-bundle lint <dir>`**：离线校验九要素完备性、YAML Schema、引用完整性（Action 引用的 Object 是否存在、Logic 引用的字段是否在 Object 属性表中）、`SYNTHETIC_PILOT` 水印在场性及 G9 零敏感数据残留扫描（严禁含真实 IP/手机号/企业实名）。
2. **`ontology-bundle test <dir>`**：离线加载 `fixtures/synthetic_samples.jsonl`（含 5 类注入脏数据），在本地直接调用 `logic_engine` v2 跑全部规则断言，毫秒级出回归报告，无需起全套容器。
3. **`ontology-bundle diff <dirA> <dirB>`**：输出语义级变更摘要（新增对象、字段类型变更、破坏性删除告警 `BREAKING_CHANGE`）与精确 `out_of_box_rate` 预估。
