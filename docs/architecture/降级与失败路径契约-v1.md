# 降级与失败路径契约 v1（架构评估 P3-8 / P3-10 / 第六图文字底本）

> 状态：已落地（文档层）｜日期：2026-11-08｜范围：服务端运行期
> 定位：把「Redis 挂掉会怎样」「worker 能开几个」这两件**只存在于口头共识**的事，
> 写成带 `file:line` 锚点的可核对契约，并作为第六张架构图
> （`docs/architecture/archify-diagrams/degradation/`）的文字底本。
> 本文件**只描述现状**，不改实现；发现的缺口如实登记在 §4，不代决策。

---

## 0. 一句话

**事实与状态在 PostgreSQL，Redis 只承载易失态与派发信号。**
因此：Redis 不可用 ⇒ *新任务投不出去*（队列停摆），但*已落库的事实不丢*；
Worker 横向扩缩容当前**不建议**——队列弹出即出队（LPOP）、单活守卫是「查-建」两步，
多实例会把这两个窗口的丢失面按实例数放大（§2）。

---

## 1. Redis 降级行为（P3-8）

### 1.1 Redis 在本仓到底承载什么（现测清单）

| 面 | 载体 | 锚点 | Redis 挂掉的实际后果 |
|---|---|---|---|
| **派发信号**（哪个 job 该跑） | Redis list `fde-jobs` | `server/src/fde_api/jobs/queue.py:29-40` | `enqueue` 抛 RedisError → **新任务投不出去**；`dequeue` 抛 RedisError → worker 循环中断 |
| **任务事实与状态** | PG `background_jobs`（status/attempts/locked_until/locked_by） | `server/src/fde_api/jobs/worker.py:99-143` | **不受影响**——状态、租约、重试计数都在 PG |
| **事务性 outbox** | PG `outbox_events` | `server/src/fde_api/jobs/outbox.py:29`（写）、`:50`（投递） | 事件行仍在 PG；Redis 恢复后由 reconcile 补投 |
| 登录失败计数 | Redis（`fde:login-fail:*`） | `server/src/fde_api/auth/routes.py:37-72` | **默认 fail-open**（放行 + WARNING）；`FDE_LOGIN_RATE_FAIL_CLOSED=1` 切 fail-closed（429） |
| AI 确认「密码错次数」 | Redis（`fde:ai:confirmation-failures:*`） | `server/src/fde_api/control/api_actions.py:261-266` | **无守卫** → RedisError 直接冒泡成 500（不是 429）——见 §4-① |
| AI 执行状态与事件流 | Redis（TTL 键 + list） | `server/src/fde_api/ai/executions.py:70,95,172-194` | 状态读不到 → 「AI 执行记录不存在或已过期」（404）；**任务本身在 PG**，不丢单 |
| 行业模板生成「取消」标记 | Redis（TTL 键） | `server/src/fde_api/ai/industry_template_service.py:126,234` | 取消标记写不进去 → 该次生成取消不掉（功能降级，不影响事实） |
| 就绪探针 | `redis_client.ping()` | `server/src/fde_api/health/routes.py:19` | `/ready` 报 Redis 不可用 |

### 1.2 停摆与自愈的边界（诚实版）

- **队列停摆 = 新任务进不来，不是任务消失**。`outbox_events` 与 `background_jobs`
  的行都还在 PG；Redis 恢复后由两条自愈路径补回：
  ① worker 循环里的周期对账（`server/src/fde_api/cli.py:191-193`，周期 60s，
  `RECONCILE_INTERVAL_SECONDS`）；
  ② outbox 侧的补投（`server/src/fde_api/jobs/outbox.py:50` 的 dispatch_pending，
  含「已 dispatched 但未落终态」的第三候选与迟滞窗）。
- **已在跑的 job 不受影响**：租约与心跳都在 PG（`locked_until` 5 分钟，
  `LEASE_MINUTES = 5`，`server/src/fde_api/jobs/worker.py:41`）。
  worker 进程若因 RedisError 退出，租约到期后由 reconcile 捞回并标
  `worker_lost`（工作流侧：`server/src/fde_api/workflows/recovery.py:46`，
  run failed + 悬挂节点 failed，产物未落表即未发生）。
- **登录不因 Redis 挂掉而被挡住**（默认档）：限流器不可用时记 WARNING 并放行
  （`server/src/fde_api/auth/routes.py:63-71`）——这是**显式选择**，不是静默漏网；
  对外暴露的部署用 `FDE_LOGIN_RATE_FAIL_CLOSED=1` 切到「一律按超限处理」。

### 1.3 永不降级项（红线，Redis 与否都一样）

以下动作**不得**因为任何依赖故障而走「降级替身」路径：

- 对外发信（`file_send_wechat` 等，`api_catalog` 的 G6 档）；
- 写类外呼（`api_actions` 的写操作，须走确认闸与幂等键）；
- 付款 / 收款 / 结算；
- 门禁裁决与拍板（`gates` 状态机）。

它们的事实与闸门都在 PG 事务里，依赖故障时应**失败并留痕**，而不是「先做了再说」。

## 2. Worker 横向扩缩容边界（P3-10）

### 2.1 已经安全的部分（多 worker 也不会重复执行的依据）

| 机制 | 锚点 | 作用 |
|---|---|---|
| 行锁领单 + 租约 | `server/src/fde_api/jobs/worker.py:99-143`（`with_for_update=True` + `locked_until` + `locked_by` token） | 同一 job 不会被两个 worker 同时领走 |
| 租约续期 | `server/src/fde_api/jobs/worker.py:231-259`（`_renew_lease`，token 绑定 job id） | 长任务不被误判为失联；续期只延长自己的租约 |
| 单活守卫 | `server/src/fde_api/jobs/queue.py:51-73`（`ensure_background_job` 按 (job_type, target_id)） | 同一目标同时只有一个活跃 job |
| 节点级幂等键 | `server/src/fde_api/workflows/dispatch.py:540`（写类 call 节点落 sha256，与 api_actions 同构）；agent 节点 `wfnode-{行id}:{attempt}` | 重试/崩溃恢复不二次外呼 |
| 失联诚实收口 | `server/src/fde_api/workflows/recovery.py:46`（run failed + 节点 failed，产物未落表即未发生） | 崩了不会伪装成 done |
| 跳数熔断 | `MAX_RUN_HOPS = 8`（`server/src/fde_api/workflows/constants.py`） | 拍板重投链不无限增长 |

### 2.2 当前**不宜**横向扩的三个理由（现状即边界）

1. **队列弹出即出队**：`JobQueue.dequeue` 用 `LPOP`
   （`server/src/fde_api/jobs/queue.py:32-40`），不是可靠队列（无 processing 队列、
   无 ack）。worker 弹出后崩溃 → 该 job id 从 Redis 队列消失，只能靠 PG 侧
   `locked_until` 过期后由 reconcile 捞回。**这个窗口的丢失面随 worker 数放大。**
2. **单活守卫是「查-建」两步**：`ensure_background_job` 先查活跃行再插新行，
   **没有数据库唯一约束兜底**（`server/src/fde_api/jobs/queue.py:51-73`）。
   单 worker 时竞态窗口小；多实例并发 dispatch 同一 (job_type, target_id)
   可能建出两条活跃 job。节点级幂等键能挡住「重复执行」，但**挡不住重复建 job**
   与重复计费/重复事件。
3. **心跳与对账周期未按实例错峰**：`beat()` 写心跳（TTL 180s）与
   `RECONCILE_INTERVAL_SECONDS = 60`（`server/src/fde_api/cli.py:26,191-193`）
   在每个实例上都从进程启动时刻起算。多实例同时 reconcile 同一批无主作业，
   会把「温和的补投」变成「同时补投」——目前靠幂等键兜底，但属于**运气成分**。

### 2.3 真要横向扩，先补这五件（清单，不是排期）

1. 队列改**可靠弹出**（`BRPOPLPUSH` / `LMOVE` 到 processing 队列 + 超时回收），
   或干脆改用 PG 侧 `FOR UPDATE SKIP LOCKED` 领取（队列与事实同库，少一份状态）。
2. `background_jobs` 加 **(job_type, target_id) 活跃唯一约束**（部分唯一索引），
   让单活守卫由数据库兜底，而不是应用层「查-建」。
3. **按 job_type 分片**：不同 worker 只领自己那类 job；前提是所有实例注册同一套
   handler（现状 handler 是进程内注册表，`ensure_default_handlers()` 在 worker 入口
   显式补注册，`server/src/fde_api/cli.py:174-176`）。
4. 心跳与 reconcile 周期**按实例错峰**（实例序号取模），避免同时扫同一批。
5. 幂等键覆盖到**所有**有外部副作用的路径（现状：写类 call 节点已覆盖；
   人工审批与 agent 节点靠 attempt 代际与人工门）。

> **本轮不改实现**：P3-10 的交付口径是「把边界写清楚并可核对」，扩缩容是独立的
> 架构变更，需要单独的拍板与迁移窗口。

## 4. 如实登记的缺口（本轮不修）

| # | 缺口 | 锚点 | 后果 | 建议处置 |

| ① | AI 确认的「密码错次数」计数无 Redis 守卫 | `server/src/fde_api/control/api_actions.py:261-266` | Redis 挂 → 500（而非 429），确认闸的限流语义失效 | 与登录限流同款：显式 fail-open/fail-closed 二选一 + WARNING |
