# ADR-003：收入科目层与项目级派单结算分层——不改 `delivery_settlements`，份额算法复用 `seat_shares_for`

- **状态：** Accepted（G0 裁决，2026-11-08）
- **消解歧义：** 任务书 §0.3（T-13 分账结算与既有 `dispatch/settlements.py` 的边界）
- **基线：** `eee317c`

## 1. 背景（实测）

- `dispatch/settlements.py` 已有：`seat_shares_for(session, package)`（四席位份额实算，`settlements.py:59`）、`delivery_settlements` 表（`dispatch/models.py:388`）、`dispatch_rule_versions`（权重唯一来源=版本表，`:353`；快照键 `rules.py:25`）、`disputes`（`:449`）。这些是**项目级派单结算**（一个交付项目成交后四席各分多少），派单引擎 r1–r11 已闭环。
- T-13 的「培训费、席位费、项目分成分别记账」是**收入科目分离**（平台收入按科目可核对），与项目级分账**不是同一层**。
- 分成比例 Q11 拍板「按角色与项目类型配置」→ 本期不定数。

## 2. 裁决

1. **禁止在 `delivery_settlements` 上加列硬塞科目**。科目层独立新建：收入类型 → 金额 → 关联对象（订单/席位/分成事件），通过外键指回既有结算与报价/合同对象（`quotes` `workbench/models.py:643`、`payments` :753、`contracts` :801）。
2. **席位份额计算继续复用 `seat_shares_for`，不得另起算法**；科目层在分成事件上引用其结果，不重算。
3. **项目分成比例本期不定数**：只落「按角色与项目类型配置」的结构（配置位缺省不预写业务数值），数值待试点数据（任务书 §17-4）。
4. 六项计费名目（软件订阅／企业订阅／使用量／项目费／软件服务费／平台分成）**只定义归属，不定义计算方式**；结账金额本期走线下约定。
5. 科目层的写路径属高风险写，默认人工确认 + 审计事件（同 ADR-002 §2.5 模式）。

## 3. 理由

- 两层的读法不同：分账表按「项目×席位」读，科目账按「科目×期间」读；塞同一张表会让任何一方查询都要过滤另一半的行。
- `delivery_settlements` 已被派单 r 系测试与规则快照钉住（16 个 dispatch 测试文件），加列会引发快照与序列化连锁改动，违反「不改动 V3.1 在跑线」边界（任务书 §1.3）。
- 指回 quotes/payments/contracts 使科目账可与既有收款台账对账（活库已有 quotes=1/payments=3 的真实使用）。

## 4. 后果

- G3 需要新科目表 + 迁移；「三类科目分别可查、可对账」为其验收（任务书 §7）。
- 「套餐含席位不重复收」反例用例（L2 9800／L3 19800／L0 首单三组合）在席位激活流（ADR-002 订阅权益）上落，科目账只记录已发生的费。

## 5. 与任务书裁决要求的对照

| 任务书 §0.3/§7 要求 | 本 ADR |
|---|---|
| 禁止 `delivery_settlements` 加列硬塞 | §2.1 ✅ |
| 新增科目层 + 外键指回既有对象 | §2.1 ✅ |
| 份额复用 `seat_shares_for` | §2.2 ✅ |
| 分成比例不落数、只落配置结构 | §2.3 ✅ |
| 六名目只定义归属不定义计算 | §2.4 ✅ |
