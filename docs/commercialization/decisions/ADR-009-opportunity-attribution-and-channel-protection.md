# ADR-009：商机归属与渠道保护——七步链路、可配置规则结构与保护期封堵钩子

- **状态：** Accepted（G4 成文，2026-11-09）
- **消解：** 任务书 §8（T-09 商机归属与渠道保护）的落地歧义
- **基线：** fork/main `9497b2c`（G3 收口态）
- **配套成文规则：** `docs/commercialization/rules/opportunity-attribution-rules.md`（**规则唯一成文处**）

## 1. 背景（实测）

- G0 基线审计 §2 表格：商机归属**无对应模块**（`docs/commercialization/00-baseline-audit.md`）——本域从零新建。
- G1 已落角色分层 R1–R4（`commercial_entitlements.commercial_role`）：**R2 创业者**是报备人、**R1 企业**是需求确认方——本域以该分层为准，不另造角色枚举。
- G3 已落收入科目层 `commercial_revenue_ledger`（三类科目，项目分成行 `subject_type='project_share'`）——第 7 步「按既定分成规则结算」**引用**该层，不建第二套结算。
- 既有 `dispatch/channel_guard.py` 已实现**私单封堵**三条钩子：H1 派单线立项仅平台侧、H2 池内企业直签封堵（422 `private_deal_blocked`）、H3 交付包只能建在派单线项目。**H2 的判据是「企业已进派单池」**——即「成交后」；而「报备→归属确认→撮合之前」这段窗口**无任何保护**。
- 任务书 §8 的硬约束：规则数值（保护期长度、续期条件、归属判定）**本期不定数**——须以**可配置结构**落地，成文前以配置态留空兜底，**不留硬编码默认值**；**商机保护不得变成永久锁定企业**；**已确认归属的商机，企业后续直接注册不得简单转移**。

## 2. 裁决

1. **七步链路按状态机落地**（成文规则 §2）：`submitted → enterprise_confirmed → attribution_confirmed → presales → matched → settled`，另有 `disputed` / `withdrawn` 终态旁支。**步 6 引用既有 dispatch 交付包**（`matched_delivery_package_id`），**步 7 引用 G3 科目层**（`settled_ledger_entry_id`）——**不建第二套撮合或结算引擎**（§1.2-9 复用优先）。
2. **规则先立框架、数值后填**（§1.2-6）：成文规则落 `docs/commercialization/rules/opportunity-attribution-rules.md`，代码侧只提供**五个配置位**（`protection_period_days` / `renewal_conditions` / `customer_choice` / `dispute_handling` / `attribution_criteria`），**迁移播种一律 `unset`**——任何路径都不得预写业务数值。**规则文件与代码配置位一一对应**由机器闸钉死（测试解析规则文件的 JSON 块 ↔ 代码常量双向比对）。
3. **保护期三态可区分**：`unconfigured`（规则未配置）／`active`（保护中，必有起止）／`expired`（已到期）。**`unconfigured` 既不是「永久保护」也不是「立即失效」**（任务书 §8 验收）。库层 CHECK 保证 `active` 必有 `protection_expires_at`——**结构上不可能出现永久锁定企业**。
4. **保护期＝直签封堵钩子（扩展既有 dispatch 封堵，非重建）**：在 `dispatch/channel_guard.py::ensure_enterprise_channel` 增一条**附加**判定——该企业存在 `protection_status='active'` 的商机时，**直签立项**被封堵（422 `opportunity_protection_active`），提示改走归属渠道；**派单线放行**、保护期未配置或已到期**放行**。钩子**惰性**（无商机即 no-op）、**失败放行**（查询异常不阻断立项，只记 warning）。
5. **归属不因企业自行注册而转移（结构性保证）**：归属与保护期是本域事实；**企业侧立项路径没有任何写路径可触碰商机行**。反例用例钉死：归属确认后企业以同一企业代号直签立项 ⇒ 商机归属人、归属时刻、保护期状态**逐项不变**。商机读面派生呈现「企业后续已自助注册」这一事实（`enterprise_project_count`），使反例**非空洞**。
6. **归属确认＝关键流转，人工确认**：admin 门＋密码确认双闸（ADR-007 §2.1），逐动作 `operation_events` 留痕（带 request_id，**密码不落事件**）。**报备与撤回是当事人自证动作**（认证用户＋事件留痕，不走 admin 密码）；**企业确认**由平台代录企业书面答复（admin＋密码＋**书面依据指针＋sha256**）。
7. **规则未配置 ⇒ 相关动作一律 fail-closed 409 `rule_not_configured`**：续期（`renewal_conditions`）、客户自主选择（`customer_choice`）、争议（`dispute_handling`）、归属改派（`attribution_criteria`）四条。**归属改派尤其从严**：本期归属确认后**不存在任何转移路径**（含自动转移），直到判据规则成文并配置。
8. **客户自主选择不改归属**：客户选定的交付包写 `customer_choice_package_id`，**归属人不变**（成文规则 §5-2）——选择权是渠道内的选择，不是归属的转移。
9. **争议期间链路冻结**：商机置 `disputed` 后，撮合/结算动作 409 `opportunity_disputed`（成文规则 §6-2）。
10. **企业真实资料零入库**：本域只存企业**代号**、线索/答复/判据的**指针＋sha256 指纹**；线索材料本体留在本地 fdeops/openfde 工作目录（AGENTS 红线）。

## 3. 理由

- **放在 dispatch 封堵上而不是新建拦截层**：商机保护的商业含义就是「保护期内企业不得绕过归属渠道直签」，而既有 `channel_guard` 正是这条边界的唯一执行点；扩展它＝复用（§1.2-9），另建拦截层会造出第二套渠道闸。
- **保护期接在 H2 之前**：H2 的判据是「已进派单池」（成交后），G4 的窗口在**成交前**（报备→撮合）；两者互补不重叠。
- **规则未配置即 fail-closed**：数值未定数时，**少做**比**猜着做**安全（认证费/通过线同款纪律）；且「不配置」被显式建模为一个可区分状态，而不是静默回落到某个默认值。
- **归属改派从严**：「不得简单转移」的最强可执行形态是**没有转移路径**；等到判据成文再开放，而不是先开一个带默认值的口子。
- **报备为自证动作**：报备是创业者提交自己的线索，不是高风险治理写；把它做成 admin 门会拖慢入口且无收益（与 G2「企业自证」同款边界）。

## 4. 后果

- 新增两表（`commercial_opportunities` / `commercial_opportunity_rules`）＋ 迁移（54 rev）；商业路由 **+16**（全部不进 api_catalog）。
- `dispatch/channel_guard.py` 增一条**惰性附加判定**（既有三条钩子语义不变；无商机即 no-op）——**dispatch 域的行为变化仅限「存在 active 保护期商机且走直签立项」这一条**。
- 规则数值仍待业务拍板（任务书 §17 数值类）：配置位与成文规则已就位，填实数即可，无需改结构。
- 归属判定、企业答复采集仍走线下／平台代录；企业自助确认归 G6（企业空间）承接。

## 5. 与任务书 §8 的逐条对照

| 任务书 §8 要求 | 本 ADR |
|---|---|
| 七步链路完整（报备→企业确认→平台确认归属→保护期→售前→撮合→结算） | §2.1 ＋ 成文规则 §2（状态机逐步落库） |
| 已确认归属的商机，企业后续直接注册不得简单转移 | §2.5（结构性保证＋反例用例）＋ §2.7（本期无转移路径） |
| 保护期/续期条件/客户自主选择权/争议处理机制**写入成文规则** | 成文规则文件 `opportunity-attribution-rules.md`（§3–§7） |
| 规则数值本期不定数，可配置结构落地，不留硬编码默认值 | §2.2（五个配置位＋迁移播种 unset＋机器闸） |
| 商机保护不得变成永久锁定企业 | §2.3（`active` 必有过期时刻的库层 CHECK）＋ §2.4（到期即放行） |
| 验收①归属确认后企业自行注册，商机不自动易主（≥1 反例） | §2.5 反例用例（归属人/时刻/保护期三态逐项不变） |
| 验收②保护期为空时行为是「未配置」，与「永久保护」「立即失效」可区分 | §2.3（三态 ＋ 三种不同行为：未配置→放行且标注、active→封堵、expired→放行） |
| 验收③规则文件与代码中的配置位一一对应 | §2.2（机器闸：规则文件 JSON 块 ↔ 代码常量双向相等） |
| 关键流转默认需人工确认（商机归属确认） | §2.6（admin 门＋密码确认＋审计事件） |
