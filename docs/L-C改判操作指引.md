# L-C 改判操作指引（人工终裁→再终裁→历史链）

> **面向**：蔡工（admin/project_lead 角色）的实际操作体会。
> **背景**：条款③写面已全落地（#517 服务端 `53b46889`＋#518 桌面 `2ad37f96`，2026-11-18，活体 524 路由／便携版 r57）。本指引只讲「怎么用」，不含开发内容。
> **一句话语义**：L-C 终裁**没有「改写」，只有「追加」**——重新提交一次人工终裁就是改判；旧行永远保留，新行成为「现行」，旧终裁派生的发现自动失效。

## 入口

桌面端（或网页端）→ **训练场** → 运行列表 → 选中目标运行 → 右栏 **「评估报告」**：

- 底部 **「人工抽检结论（L-C 终裁）」** 表单＝终裁/改判的唯一入口。
- 失败分析发现卡（同页「失败分析」区）＝发现的人工裁定入口。

## 三步体会改判流

### 第 1 步：首次终裁（如已有可跳过）

在「人工抽检结论」表单：选**结论**（通过／有条件通过／未通过／硬性失败／结论不可靠）→ 填**总分（0–1）** → **理由必填**（终裁必须留痕可追溯）→ 点「提交人工终裁」。

提交成功后该 human 层评估行落库，规则层／模型层的机器结论**原样保留并列**，不会被改写。

### 第 2 步：再终裁＝改判（核心动作）

对**同一运行**再次提交一次人工终裁（例如第一次「有条件通过」、这次改「未通过」，分数与理由按新判断填写）。

提交即改判——**无需任何额外操作**：

- 新 human 行成为**现行终裁**，报告顶部提示「人工终裁已记录：…｜现行结论：<新理由摘要>（机器原行保留并列，未改写；再提交即改判，历史行永远保留。）」。
- 评估报告里 human 行按时间编号显示 **「第 1 次终裁（已被取代）」「第 2 次终裁（现行）」**——历史链一眼可读。

### 第 3 步：观察改判的连锁效果（superseded）

改判后回到「失败分析」区，旧终裁（第 1 次）派生的发现自动**置灰失效**，卡片显示：

> 已被更新的 L-C 终裁取代（superseded）——不进蒸馏面与提案；如需重启请基于现行终裁重跑失败分析。

具体表现：

- 该发现卡的**勾选框被禁用**（不可再勾进提案）。
- 若有人试图把它带进改进提案或 AI 起草：服务端直接 **409 `finding_superseded`** 拦截（AI 调用前同样被拦）。
- 基于新现行终裁重跑失败分析，会派生**新一批发现**（新发现的「确认」状态走下面的人工裁定）。

## 发现的人工裁定（补充动作）

admin/project_lead 在未失效（非 superseded）的发现卡上可做**单点人工裁定**：

- 卡片内联表单：**裁定动作**（确认 confirmed／驳回 rejected）＋**裁定理由（必填，随发现行留痕）**→「提交裁定」。
- 状态机**单向**：`open → confirmed | rejected`，裁定后不可回翻（发现被推翻走改判路径，不走状态回翻）。
- 重复裁定返回 409 `finding_already_adjudicated`（裁定已落，不重复）。
- **confirmed 双轨**：无论发现是 L-B 推断的 `likely` 还是人工 confirmed，只要「状态＝confirmed 或置信＝confirmed」任一成立，即可进改进提案（此前只有 L-C 派生自动 confirmed 一条路）。

## 边界与纪律（实施时已钉死）

- **角色闸**：终裁与裁定均为 admin／project_lead（engineer 只读，无入口）。
- **历史行永远保留**：不改评估行不可变纪律，改判不删除、不覆盖任何历史行。
- **裁定留痕**：裁定理由随发现行 `detail_json.adjudications[]` 追加留痕（含操作人与时间），可追溯。
- **复判定纪律**：改判后若要重新出回归判定，**须新建套件**（同套件＋同提案重跑返回既有结果行＝指纹幂等）。

## 常见疑问

| 疑问 | 答案 |
| --- | --- |
| 改判会覆盖第一次结论吗？ | 不会。追加新行，旧行保留并标「已被取代」。 |
| 旧终裁派生的发现还能用吗？ | 不能。自动 superseded，勾选禁用＋提案 409 拦截。 |
| 想撤回一次误提交的终裁？ | 直接再提交一次正确的终裁即可（最新行即现行），无需删除。 |
| 谁能改判/裁定？ | admin／project_lead。 |
| AI 会自动采信哪次终裁？ | 永远只认**最新一次**（现行）；蒸馏面与提案闸均按现行终裁收敛。 |
