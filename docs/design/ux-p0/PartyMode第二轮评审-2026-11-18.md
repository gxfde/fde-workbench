# Party Mode 第二轮：确认快照与旧客户端过渡

日期：2026-11-18｜状态：升级策略已拍板，待实施｜源码基线：`81242018`

承接[首轮 R01/R02](./PartyMode首轮评审-2026-11-18.md)。本轮是模拟专家圆桌与只读契约核查，决定已回写[体验方案](./EXPERIENCE.md)；未修改产品代码或部署配置，未执行并发测试。

## 一、P0 追加发现：证据替换和裁定要共用同一个版本边界

[证据提交](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/src/fde_api/projects/gate_service.py#L288) 在锁内写清单、将目标项设为 `claimed`，并更新提交人，但不推进 `gate.version`。[裁定入口](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/src/fde_api/projects/gate_service.py#L410) 在锁内比较 `expected_revision`（目前允许省略），裁定成功时才[推进版本](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/src/fde_api/projects/gate_service.py#L575)。因此，当门禁仍是 `evidence`、其他授权和业务条件仍满足时，仅凭旧 `revision` 不能证明评审看到的仍是当前证据。行锁解决同时写入的顺序问题，不能替代确认快照。

**架构建议：复用现有门禁级 `revision`，而不是先给每个条目另建版本。** 读到清单并打开确认时冻结门禁版本和所选条目；有状态副作用的证据写入以及裁定都基于相同版本在锁内核对，证据写成功后在同一事务推进版本。校验先于证据登记、候选移除、状态更新和业务成功留痕。无论人工录入还是候选采纳，都使用同一服务规则。仅建议性的候选变化不必单独推进裁定版本；如果某个其他写路径会改变评审依据（清单引用、核验状态或提交人等），应纳入该版本规则。正式设计前复核所有实际写点，不把 `[当前仓内已见]` 当外部调用方已穷尽。

**UX 取舍：** 默认不给候选预选清单项；由用户看旧引用、新引用与「替换后回到待核验」。版本过期提示「证据或门禁状态已变，未提交。查看最新清单后重新确认」，保留尚可用的输入但清空基于旧快照的核验选择；不能只换一个版本号后再次提交。初期接受不同条目也可能互相触发刷新，因为当前门禁的提交人和状态是共享的。若真人试点证明高频互相阻塞，再评估更细的并发粒度，不先增加新状态或表。

## 二、交付登记：确认的是封存批次，不只是包 ID

[登记服务](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/src/fde_api/handover/service.py#L577) 只校验授权和 `sealed` 状态；[登记路由](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/src/fde_api/handover/routes.py#L126) 不读确认快照。[详情序列化](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/src/fde_api/handover/service.py#L323) 已提供 `manifest_sha256`、`sealed_at`、`unsealed_count` 和清单，不需要虚构“包版本号”。[解封](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/src/fde_api/handover/service.py#L556) 会令旧确认失效。

**建议契约：** 管理员确认框显示包名、件数、封存时间和摘要；实际提交绑定确认框打开时的完整 `manifest_sha256` 及 `unsealed_count`（封存批次的现有可比标记）。服务端在同一事务锁内复核项目授权、管理员角色、封存状态和这两个预期值，再登记并写业务成功事件。编辑清单、封存、解封、登记须使用同一包的锁定规则，防止清单读写绕过保护。讨论中字段名称和错误码为建议、不是已发布契约；不增加登记权限、不改状态机，不把登记说成客户签收或付款。

**UX 取舍：** 预期不符显示「封存清单已变，未登记。请重新查看并确认」。取消零写入。超时后只查包状态和实际摘要；查到同版已登记可以展示对象终态，但无本次写回执不宣称是当前用户这次提交完成。若登记的是其他批次，不报本次成功，不盲重发。

## 三、旧客户端：分开保住读能力与高风险写入

仓内确认的调用方：桌面门禁页的[统一提交](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/desktop/src/renderer/src/projects/GateBoard.tsx#L233)、桌面封包页的[状态操作](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/desktop/src/renderer/src/handover/HandoverPackagesPanel.tsx#L288)、[贯通脚本登记步骤](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/scripts/verify/verify_order_to_delivery_e2e.py#L453)，以及[现有后端测试中的无请求体登记](https://github.com/caishide/fde-workbench/blob/812420186853f75ae1c9bfd66479b2a19aeb839f/server/tests/test_handover_packages.py#L195)。实际在用安装包、同构网页、仓外人工操作脚本需由发布负责人再盘点。通过仓内静态搜索不能证明不存在仓外调用。

| 阶段 | 推荐发布规则 | 验收条件 |
|---|---|---|
| 服务端先支持，联调验证 | 现有路由支持条件写并明确宣告其语义。允许缺少条件的阶段只用于迁移/联调，不宣称 P0 已关闭；若生产切换前无法同步升级，可缩短兼容窗口或暂缓相关高风险操作。 | 新客户端不能只看详情有摘要或 `revision` 就判定受保护：旧服务端也有这两个字段。必须有可验证的契约能力标志或等效受保护入口；缺少时，新端不要提交这些高风险写入。 |
| 切严格 | 更新桌面、同构网页和脚本后，交付登记、门禁证据提交及裁定要求各自的确认条件；省略不走无条件旧实现。老客户端保持能查看，不支持的写动作明确引导升级；执行人/裁定人隔离、企业与项目授权等原闸不变。默认建议旧版首次提交也一并收紧：该动作同样会改变门禁状态、提交人和裁定依据。 | 授权的旧端无条件请求明确失败，未授权仍按原权限口径处理，不回传快照细节；新端对旧服务端也不发送不受保护的写入。冲突需重新预览，人再次确认，脚本不代人拍板。 |
| 回退 | 客户端可以回退，严格服务端仍挡缺条件写入。若必须回退服务端且会丢保护，先按发布方案暂停这些写操作，恢复后重新读并确认。 | 不把旧无条件写入当应急旁路；切换前明确操作负责人、暂停动作影响范围、验证出入口和恢复条件。 |

## 四、发布前必须补的验收

| 编号 | 测试 | 可观察结果 |
|---|---|---|
| B01 | 两会话：A 确认旧包，B 解封后重封（含同一清单重封），A 提交。再分别验证登记与解封、两次登记真正重叠。 | 旧确认写入被拒且无登记事件；并发分支至多一个登记成功，包状态、摘要与审计一致。 |
| B02 | 两会话：A 在空项或旧引用上打开替换确认，B 先提交，A 再提交；另测同来源同指纹但共享提交人或核验状态已变化。 | A 不得改清单或新增证据、剪除候选、写成功审计；界面明确要求按新快照确认。 |
| B03 | A 打开门禁裁定，B 更新证据，两人符合既有职责分离；A 带旧版本裁定。再验证最新快照下的合法裁定。 | 旧版裁定被拒，不能使新证据变为已核验；刷新重核后仍可按原权限和门禁规则办理。 |
| B04 | 新端/旧端 × 新服务/旧服务；严格模式缺条件、冲突、超时回读、非授权，以及服务端回退演练。 | 上线门槛以服务端拒绝无条件写为准；失败不写成功事件、不暴露额外快照信息。回退演练不恢复无条件写入。 |

B01–B03 除界面验证外，还需要隔离的 PostgreSQL 双连接测试（既测连续变更后的旧确认，也测真实事务重叠）；SQLite 或请求 mock 不能证明行锁行为。所有写测试使用合成项目，禁止拿真实交付作样例。

**蔡工拍板（2026-11-18）：受控迁移后严格。** 先联调验证受保护写入并约定切换时间；切严格后，未升级端保留原有授权读能力，交付登记、门禁证据提交、门禁裁定必须升级后才能办理。服务端回退若会丢失保护，先暂停这些写操作，不开无条件写入旁路。此次只确认方案，未授权开发、发布或部署。
