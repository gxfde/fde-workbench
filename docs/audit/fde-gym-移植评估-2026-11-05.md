## 0. 结论先行

### 0.1 它是不是「交付产物评测」项目？——**部分属于，但必须正名**

`[已核实]` README.zh-CN.md 自称「新时代的 OJ：超越代码，聚焦于端到端」，评测方式是「把你交的系统上线，跑客户没给你看过的流量，看客户自己的指标好了多少」。

| 若「交付产物评测」指… | 判定 | 依据 |
|---|---|---|
| 对**交付文档/方案/SOP/代码包**做质量打分、合规检查 | **不是** | 仓库无文档打分器；`judge.py` 只判「客服回复 vs 标准答案」，是题库内部的小工具 |
| 对**交付结果**（上线后系统）做效果量化与验收 | **是** | `run.py::grade_workspace` 回放隐藏流量算 `uplift`；`standings.ts` 出 verdict |
| 一个可嵌入业务系统的评测引擎 | **不是** | 它是**独立训练/竞技平台**（题库、账号、排行榜、在线工作终端、coding agent），不是库/SDK |

**准确定位**：`[已核实]` **FDE 端到端交付能力的在线判题 / 基准测试平台（OJ / benchmark + 训练场）**。评测对象是「被交付的、运行中的系统」在**未公开流量**上的**客户业务指标提升**；附带评价交付过程（问人成本、事故、越界、篡改）。

### 0.2 它能补齐我方哪一块能力？——**「交付效果的结果验收层」**

`[已核实]` 我方现有四层，**没有一层回答「这次交付让客户业务指标变好了多少、这个结论能否被反证」**：

| 我方现有层 | 回答的问题 | 实测依据 |
|---|---|---|
| G1–G9 门禁 | 证据齐不齐、能不能过门（**合规闸**，人工核验） | `projects/gate_service.py`：pending→evidence→passed/conditional_pass/failed，`claimed≠accepted`，证据只存 `source_uri+content_hash`；`server/seeds/gates.json` G8/G9 |
| 方案健康分 | 模板/引用/报价填没填全（**静态完备性**） | `solutions/service.py:950` `solution_health`：覆盖率+引用完整性+报价合法性 |
| 试点 / 指标报表 | 过程跑得怎么样（**效率**） | `agents/pilot.py`「只出数、不判阈」；`metrics/service.py` 只读聚合 + `insufficient_data` |
| 派单仿真 | 撮合引擎比随机基线好多少（**内部仿真**） | `dispatch/simulator.py`：固定 seed、显式假设表、随机基线对照；`docs/dispatch-sim-r9-seed42.json` 0.9565 vs 0.9183 |

`[已核实]` 全仓 `.py` 对 `uplift` / `kpi_baseline` / `kpi_oracle` / held-out / hidden traffic **零命中**。

**fde-gym 补的三件东西**（这是它唯一真正值钱的部分）：
1. **结果指标可计算**：`uplift = (kpi - kpi_baseline) / (kpi_oracle - kpi_baseline)`，0=什么都没改、1=参考解、≥0.8 通过。
2. **结论可反证**：`run.py validate` 用 `do_nothing` / `literal` / `oracle` 三锚点 + `shortcut` / `bypass` / `memorised` / `alternate` 四类反例 + 跨变体均值，证明「这道题测的确实是它声称测的东西」。
3. **评测过程可信**：隐藏真相隔离、问话日志 HMAC 链 + 外部 ledger 防篡改、`incidents` 判负、过程成本计入 `uplift_net`、`harness_version` 写进每份 `result.json`。

> `[已核实]` 特别契合点：`server/seeds/gates.json` 的 **G9「上线门」exit_condition 明写「验收线达成」**，但现状是清单项 + 客户 owner 拍板，**「验收线怎么算」没有机器可读协议**。这正是移植落点。

### 0.3 移植裁决

**有条件采纳：只移植「评测协议与判据」，不移植平台、不引入代码/依赖/运行时。**

- 理由 A：`[已核实]` 站点全家（账号/排行/在线终端/NPC 客户人员/coding agent）在 B2B 真实客户交付场景无业务承载，且会撞我方红线。
- 理由 B：`[已核实]` 「grade＝启动被交付的代码」与我方「审查不执行被审代码」「交付禁跑客户代码」直接冲突。
- 理由 C：`[已核实]` 我方已有 `dispatch/simulator.py` 的固定种子 + 假设表 + 基线对照 + 口径 simulation 纪律，**同构基建已存在**，只需扩协议而非另起炉灶。

## 2. 代码结构与关键模块

`[已核实]` 全树约 8,405 行（Python harness 3,000+ / TypeScript app 5,000+），两个几乎独立的子系统：

```
fde-gym/
├─ harness/          Python 3.9 标准库，零第三方依赖，评测引擎（版本 1.3.0，独立打 tag）
│  ├─ run.py  760   主入口 new/serve/grade/validate/spend；uplift 公式、三锚反证、ledger+HMAC
│  ├─ bench.py 886  批量跑模型：5 工具、预算/断点续跑、result.json、table
│  ├─ isolate.py 324  环境擦除(FDEGYM_*/ *_API_KEY/ *_TOKEN) + macOS sandbox-exec + 独立 uid
│  ├─ npc_server.py 512  客户方人员：脚本化回答 + LLM 路由 + topic gate + HMAC 日志链
│  ├─ audit.py 194  agent transcript 越界扫描（clean/check/violation）
│  ├─ judge.py 74  LLM 判客服回复 correct/wrong/deferred，按内容哈希落盘缓存
│  ├─ launch.py 26 / llm.py 221 / llm_gateway.py 86 / ask_client.py 92 / pilot_client.py 30
│  └─ models.json  模型表（价格用 provider 实际数）
├─ app/             TypeScript：Hono + React19 + Vite8 + pnpm，站点与 runner
│  ├─ server/harness.ts 616  站点驱动 harness；SITE_SECRET 正则过滤不给 harness/env
│  ├─ server/runner-api.ts 115  Runner 接口（24 方法：createRun/serve/npc/grade/exec/agentTurn…）
│  ├─ server/session.ts 492 / standings.ts 144 / runners.ts 262 / pi.ts 246 / db.ts 256
│  └─ web/  题库/工作台/提交/排行/管理台页面；lib/score.ts 分数口径
├─ scripts/  fetch_cases.py（HF 下载）/ smoke_cases.py / cutout.swift
├─ docs/     self-hosting.md（配置 + Security）；images/
├─ docker-compose.yml  postgres / storage(S3) / gym / runner 四服务
└─ .github/workflows/checks.yml  app(typecheck+test+build, PG16) / harness(compileall on Py3.9)
```

**架构要点** `[已核实]`：
- **站点与 runner 分进程**：站点不执行用户代码，runner 不持数据库/对象存储/模型密钥；两者在隔离网络。
- **每个 run 一个系统用户**（容器内 root + `FDEGYM_EXEC_UID_BASE`），工作区属该用户，题目/参考解/harness/其他 run 均不可读。
- **密钥只从文件读、不从环境变量读**（`FDEGYM_OPENROUTER_KEY_FILE`），因为环境变量会被被交付代码继承；1.1.0 修的正是 1.0.0 的密钥继承漏洞。
- **题目是插件数据**：`NEEDED = ("engagement.json","npcs.json","build_world.py","grader.py")`，另有 `truth.json` / `briefs/` / `solutions/` / `variants.json`；`grader.py` 由 harness 动态 `importlib` 加载。

## 4. 与现有交付系统的契合点和缺口

### 4.1 契合点（可直接对齐，非零起点）

| fde-gym 机制 | 我方已有等价物 | 结论 |
|---|---|---|
| 固定 seed + 显式假设表 + **基线对照** + 口径 `simulation` 不冒充真实数据 | `dispatch/simulator.py`（seed=42、`DEFAULT_ASSUMPTIONS` 全量回显、`_random_assignment_baseline`、报告 meta 逐字回显） | **同构，直接扩协议即可** |
| 样本不足不编数值 | `metrics/service.py` `status="insufficient_data"` | 口径纪律一致 |
| 证据只存指针 + 指纹、原件留工作目录 | `project_evidence` / `gate_service` `source_uri + content_hash` / AGENTS.md 红线 | **红线完全一致** |
| 规则版本快照 + 不可变版本 | `WorkflowDefinitionVersion`（不可变） | 可承载 `engine_version` |
| 审计留痕 / 写操作幂等 | `OperationEvent` / `api_actions` sha256 | 可承载 HMAC 链的等价物 |
| G9「验收线达成」 | `server/seeds/gates.json` G9 exit_condition | **最精准的落点** |

### 4.2 真实缺口 `[已核实]`

1. **无结果指标协议**：全仓无 `kpi_baseline` / `kpi_oracle` / `uplift`；G9「验收线」是文字清单 + 人工拍板，机器不可算、不可复现。
2. **无反证/防作弊判据**：`docs/audit/开源项目借鉴总览-2026-11-05.md` #11 已登记「门禁一正一反判据成文」（P1，来自 GIIP），但**仅有一正一反**，无三锚点、无 shortcut/bypass/probe、无跨变体防背答案。
3. **无「过程成本计入结果」**：我方 `platform_hours_share`、`单会成本` 只作报表指标，不进验收分数；fde-gym 的 `uplift_net = uplift - contact_cost` 把「打扰客户方的人」变成扣分项。
4. **无事故/篡改判负语义**：我方门禁 `failed` 允许重交证据；fde-gym 是「一次交付、一次判分、`incidents` 直接 ≤0」。
5. **无评测输入隔离**：我方证据表存指针，但「被评方不可写评测真相」这一层没有独立账本（ledger）语义。

### 4.3 明确不适用（不要硬套）

`[已核实]` 我方是**真实 B2B 客户交付管理与合规系统**，不是训练场：客户是真实甲方（不是 LLM NPC）、交付物多为文档/方案/工作流/证据（不是可启动的 `system/`）、且 AGENTS.md 红线禁止客户真实资料入库、禁止交付进程跑客户代码。因此题库、NPC、在线终端、排行榜、账号体系、coding agent、`pi-coding-agent` 全部无落点。

### 5.1 可直接复用（`[已核实]` 均为协议/判据，非代码搬运）

|---|---|---|---|
| R1 | `uplift` 归一化公式 + 0/1 双锚 + `PASS=0.8` + 分数**截断不四舍五入** | 写进《交付效果评测协议 v0》，纯文档 | **P0** |

## 7. 关键改造点（开发视角）

1. **评测对象契约化**（阻塞项）：先定 `deliverable_contract`（entrypoints / 输入快照 / `metric_fn` / 允许副作用），否则 `grade` 无法实现。建议从「方案文档 + 门禁清单 + 工作流定义」这类**可静态回放**的产物起步，不碰可执行客户代码。
2. **指标注入而非硬编码**：`kpi_baseline` / `kpi_oracle` / `kpi` 从业务配置注入；`kpi_oracle == kpi_baseline` 时 `span=0` → 按 fde-gym 口径返回 0 而非除零；**无 oracle 时不得出分**，返回 `insufficient_data`。
3. **三锚点必须可复现**：同 seed、同假设表、同 `engine_version` 两次结果一致；`do_nothing` 必须 ≈0（这是我方 `simulator` 已有「随机基线」的自然延伸）。
4. **红线适配**：客户资料代号化；真相/参考解/隐藏流量不入库不进 git；评测输入放被评方不可写位置（ledger 语义）；文件落点纪律写进 AGENTS.md。
5. **完整性判负**：评测日志链式签名 + 外部账本计数；任一不一致 → `incidents` → 分数 ≤0 + `OperationEvent` 留痕（对齐「可解释性」要求：卡在哪一跳、证据在哪）。
6. **版本化 result**：每份结果必带 `engine_version` / 规则版本快照 / `seed` / 假设表全量回显 / 口径 `simulation|live`；**禁止把合成结果冒充真实业务数据**（我方 simulator 已有此纪律，直接沿用）。
7. **不执行被评代码**：把 fde-gym「grade 会启动交付系统」整段替换为「只读回放 + 静态检查」；`R7` 的越界扫描只作清单，不引入 `sandbox-exec`。
