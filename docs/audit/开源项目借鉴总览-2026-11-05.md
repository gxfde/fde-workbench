**为何不是 FF-FDE-Delivery-Workbench**：它是**同类系统**（八阶段 FDE 交付工作台），可抄的具体实现最多（清单 #27–#34 共 8 条，是九个项目中单轮贡献条目最多的），但**不能作为整体架构源**——它把官方 DSH 运行时整仓 vendored 并以 TypeScript/Node 24 插件双轨运行，我方是 Flask + PostgreSQL + React 的多租户合规系统；且其门禁是单项目单机、无项目级 RBAC，八阶段与 G1–G9 不兼容。故裁决为「**只借鉴实现，不引入运行时**」。它的 DSH 内置虽是用户最关心的点，但对我方协议不兼容（§0 专项结论 ④），恰好说明「有源码 ≠ 能接上」。

> **维度区分（防误读）**：本裁决回答的是「哪个项目的借鉴**现在最划算、最能直接落地**」。若用户 Q1/Q2 拍板确认要做「上线后业务结果验收」的产品化能力，**fde-gym 会成为该方向上最有价值的输入**，与本节裁决不矛盾——前者是工程借鉴性价比，后者是产品战略价值。**2026-11-06 拍板已确认方向为「结果验收」，但因缺真实客户 KPI 与 oracle 证据维持文档级，与本节裁决不冲突。**

### 3.7 关键改造点（开发视角）

1. **评测对象契约化（阻塞项）**：先定 `deliverable_contract`（entrypoints / 输入快照 / `metric_fn` / 允许副作用），否则 `grade` 无法实现。建议从「方案文档 + 门禁清单 + 工作流定义」这类**可静态回放**的产物起步，不碰可执行客户代码。
2. **指标注入而非硬编码**：`kpi_baseline`/`kpi_oracle`/`kpi` 从业务配置注入；`kpi_oracle == kpi_baseline` 时 `span=0` 返回 0 而非除零；**无 oracle 时不得出分**，返回 `insufficient_data`。
3. **三锚点必须可复现**：同 seed、同假设表、同 `engine_version` 两次结果一致；`do_nothing` 必须 ≈0（是我方 simulator 已有「随机基线」的自然延伸）。
4. **红线适配**：客户资料代号化；真相/参考解/隐藏流量不入库不进 git；评测输入放被评方不可写位置（ledger 语义）；文件落点纪律写进 AGENTS.md。
5. **完整性判负**：评测日志链式签名 + 外部账本计数；任一不一致 → `incidents` → 分数 ≤0 + `OperationEvent` 留痕（对齐「卡在哪一跳、证据在哪」的可解释性要求）。
6. **版本化 result**：每份结果必带 `engine_version` / 规则版本快照 / `seed` / 假设表全量回显 / 口径 `simulation|live`；**禁止把合成结果冒充真实业务数据**（我方 simulator 已有此纪律，直接沿用）。
7. **不执行被评代码**：把 fde-gym「grade 会启动交付系统」整段替换为「只读回放 + 静态检查」；R7 越界扫描只作清单，不引入 `sandbox-exec`。
