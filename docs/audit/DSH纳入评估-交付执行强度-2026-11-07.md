# 是否将 DSH 纳入当前方案——交付执行强度专项评估

> 评估日期：2026-11-07（晚）　｜　性质：**只读评估轮**，零代码零配置零安装。
> 问题框架：**「加入 DSH 能否使交付执行层面足够强大」**——不是「能不能装」，是「装了值不值」。
> 基准：`fork/main` `a139aba`（权威，本地 main 落后 16 提交）；审计清单 314 行（fork/main）；pytest 2101=2095+6s（CI run 42343361485）；路由现测 304。
> 既有决策链：B#27（`docs/architecture/DSH-适配层决策记录-v1.md`，维持不装）→ 借鉴总览 Q8（不立项自写适配层、#27 留立项书备选）→ 售前方案 v1.2 Q5（zcode 唯一优先；DSH 不作为第二家编码智能体）→ 多专家评审确认。**本轮问题正是 Q5 已留的「未结案」后项，须按其口径回答，不得绕过。**

## 0. 结论摘要

**不加入。DSH 不能使交付执行层面变强——因为「交付执行弱」这个前提本身不成立，而 DSH 恰好补不到真缺口上。**

| 判断项 | 裁决 | 一句话依据 |
|---|---|---|
| 加入 DSH 能否提升交付执行能力 | **否（边际价值≈0，负价值>0）** | 交付执行五块中四块已落地且不依赖 DSH；唯一真堵点（执行通道）是 `ZcodeAdapter` 契约错位，DSH 帮不上 |
| 「交付执行层不够强大」是否成立 | **不成立（定位误判）** | 售前方案 v1.2 §0 第 1 条已裁决：执行层已全部落地，真缺口是**执行通道（spawn 到 CLI）与售前→SOW 链路** |
| DSH 是什么角色 | **AI Server 编排层**，不是编码执行器 | 售前方案 Q5：DSH（`dsh_runtime.py:1`）与「编码执行器」不是同一位置，兼用=职责重叠 |
| 若强行加入 | **交付执行不升反降** | 适配层零实现 ⇒ 加 DSH = 先写全量 `fde-dsh-v1` 服务端（REST+回调+审批+幂等），周期远长于重写 `ZcodeAdapter`（半天级实测可解） |
| 正确的增强路径 | **zcode 执行通道打通 + T-B/T-C 阶段**，与 DSH 无关 | 见 §5 建议 |

**本轮无任何新证据触发 B#27/Q8/Q5 的重评条件**（真实 A 轨需求仍零澄清、活库 run 仍为零、官方仍无 `/v1/executions`）。三份决策文件口径一致且互相咬合，本轮维持并强化。

## 1. 先把「交付执行层面」拆成五块（混淆即答错）

| # | 块 | 干什么 | 现状 | 依赖 DSH？ |

| ② | **确定性编排** | workflow 四类节点 | `workflows/` 已落地：call/skill/agent/human_approval 四节点 + 跳数熔断（B#1）+ 强杀/崩溃对抗钉（B#14）+ 路由审计 CI 钉（#186） | **否**（skill 节点走直连降级） |
| ③ | **AI 编排/工具调用**（聊天） | AI 带工具干活 | `execute_ai_prompt` + MCP 回环；无 DSH 时诚实降级 13 只读工具 | 部分（写工具需 DSH） |

**关键事实**：用户感知的「交付执行」主要是①②⑤，这三块**已全部落地且与 DSH 无关**。④是 DSH 唯一硬依赖位，但它**不是交付执行的强度问题，是"要不要无人值守"的治理选择**——且其真前置（A 轨诉求澄清）至今为零。

## 2. DSH 对交付执行的具体价值与补充作用（诚实清单）

| DSH 能力 | 对交付执行的价值 | 判定 |
|---|---|---|
| 外部执行会话 + 版本冻结 + 回调 | 无人值守编排（A 轨） | **唯一真实价值位**——但前提是有真实的定时/事件自动化需求；当前为零 |
| MCP 回环 token 注入（写工具） | AI 聊天可调写类工具 | **已降级覆盖**：无 DSH 时 13 只读 + 写类走人工；这是治理设计不是缺陷（`ai_tool_loop.py` 注释：写类工具"designed to run behind the MCP confirmation flow"，直连面不提供是为不绕过确认闸） |
| 插件市场（`dsh_market`） | 插件分发 | 现值≈0：`dsh_market_enabled=False`、市场 URL 是占位符 `example.com` |
| 官方 harness 的 Agent 能力 | 编码执行 | **位置错误**：那是编码执行器位（zcode 轨），DSH 是编排层；Q5 已裁决兼用=职责重叠 |
| 开发者生态/更新速度 | 长期潜力 | 不构成当期价值；且 developer preview 破坏性变更反而增加维护成本 |

**结论：DSH 的全部当期价值收敛为一个条件命题——「如果需要无人值守 A 轨且愿付适配层成本」。当前前提不成立（需求零澄清、运行证据零）。**

## 3. 兼容性、成本与风险

### 3.1 兼容性：协议兼容为零（这是结构性事实，不是工程量问题）

- FDE 连的是自定 `fde-dsh-v1`（`config.py:84`）；官方源码（FF 侧 vendored `0.2.1-rc.2`）对 `/v1/executions`、`fde-dsh-v1` **零命中**（B#27 §2.2 已行号级核实）。
- 加入 DSH = **从零自写**：REST 四端点 + 五条回调 + service token + Idempotency-Key + 协议头协商 + 版本冻结落库 + 降级码映射 + MCP token 消费。参照 B#27 §3 清单。
- 官方 Python SDK（`sdk-minimal` 进程内）可缩短部分实现，但**进程内 SDK 不是网络服务**，仍需自包 HTTP 层 + 处理 Windows 服务化 + 生命周期管理。

### 3.2 成本（对照表）

| 项 | 加 DSH 路线 | 不加 DSH（打通 zcode 通道） |
|---|---|---|
| 前置 | 写适配层全量（估 2–4 周级，含回调/审批/幂等/降级全链 + 测试） | `ZcodeAdapter` 契约重写（按真实 CLI `zcode -p/--mode/--json/--cwd` 或 `app-server` stdio）+ PATH wrapper + provider 部署到 `D:\config\provider\` + 镜像钉版 |
| 已有进展 | 0（服务端零实现） | **已过半**：zcode 0.17.1 已装、provider 根因已定位（路径错位，修复=部署到 `D:\config\provider\`）、真实 CLI 形态已实测出（含 `app-server` stdio 子命令） |
| 见效周期 | 月级 | **半天实测可裁**（Q6 拍板原定即此） |
| 联调复杂度 | 需部署外部服务 + 独立 `DSH_HOME` + 安全验收七层 | 容器内/宿主侧一次实测即定 |

### 3.3 风险（加 DSH 特有）

1. **安全**：developer preview 未经安全审计（SAFETY.md 原文）；`sdk-minimal` pins `danger-full-access`；`session-log-deepseek` 默认上传会话日志 ≤8MiB/请求——与「客户资料不出本机」红线直接冲突，须显式 patch 关闭。
2. **溯源污染**：`dsh_runtime_version` 随 run 冻结落库，上游破坏性变更即污染历史溯源；回退须连带回退数据副本（FF 语义）。
3. **职责重叠**：与现有 MCP 回环/审批链重叠形成双通道，治理面翻倍（多专家评审 P0 级意见：Q5 与 Q8 未对接是「产出义务遗漏」风险源）。
4. **合规未定**：境内模型约束未拍板，DSH 默认走 DeepSeek 端点。
5. **机会成本**：把 2–4 周投给适配层，等于延迟真正能提升交付执行的 zcode 通道 + T-B（交付包）/T-C（闭环）阶段。

## 5. 结论与建议

### 5.1 明确结论：不加入

「交付执行足够强大」的真缺口清单（按阻塞度排序）：

1. **执行通道未打通**——`ZcodeAdapter.spawn_argv` 与真实 CLI 契约错位（`adapter.py:91` 调 `zcode run --task`，真实是 `zcode -p/--mode/--json/--cwd` 或 `app-server` stdio）。**这是当前交付执行唯一的执行级堵点**，与 DSH 无关，DSH 也解不了。
2. 售前→SOW 链路收尾（T-A 系列 11-07 已快速推进：A1–A9 大半落地）。
3. run 产物→`handover_packages` 交付闭环（T-B 阶段，待立）。
4. 运行证据为零（首批真实 run 后才谈 P3 梯度开放）。

**DSH 一个都补不上。**它的价值位（A 轨无人值守）是治理选择题，不是强度题；且其前置（诉求澄清+适配层立项）均不成立。

### 5.2 若坚持加入（不推荐），配套调整清单

须全部完成才可立项，缺一即停：① 先拍板 A 轨真实需求（什么任务、什么频率、谁负责）；② 按 B#27 §3 自写适配层全量（REST+回调+审批+幂等+降级）；③ 按 B#27 §4 基线锁定法登记 lock 八字段并固定 `0.2.1-rc.2`；④ 安全前置四条全过（隔离 `DSH_HOME`、关 `session-log-deepseek`、一次性 workspace、egress 限制）；⑤ 先厘清与 AI Server 编排层职责边界（Q5 落地约束原文）；⑥ 过 P3 评估报告 §11 七层验证要点；⑦ 走 goal 循环立项，与主线串行不并行。

### 5.3 不加入时，如何确保交付执行强度（正面回答）

**强度来自已落地的四层，无需 DSH：**

| 层 | 强度保证 | 证据 |
|---|---|---|
| 执行能力 | 沙箱+适配器协议+L0–L3 降级链+成本熔断+egress 白名单+产物指纹门 | `agents/` 全链；B#14 对抗钉 |
| 编排能力 | workflow 四节点+跳数熔断+审批节点+幂等代际 | `workflows/executor.py`；B#1 |
| 治理强度 | G1–G9 人工拍板、审批五要素、密码确认 15min、复核闸、事实链三源聚合、路由审计 CI 钉 | #186 漂移即红 |
| 质量底座 | pytest 2101=2095+6s、vitest 858、4 CI job、mypy 基线、变异验证纪律 | CI run 42343361485 |

**下一步真正该做的**（与售前方案 §7 一致，优先级排序）：
1. **执行通道半天实测+拍板**（Q6）：zcode 容器内可执行性 → 能则直连 `ZcodeAdapter`（重写契约段）；不能则在「openfde executor」与「Windows 宿主侧 zcode 代理」间定稿。**这一项做完，交付执行强度立即上一个台阶，成本半天级。**
2. `ZcodeAdapter` 契约重写（`app-server` stdio 优先）+ 镜像版本钉定 0.17.1 + provider 部署。
3. T-B 交付包闭环（`handover_packages`，含能力交接 item——沿用台账 §四十四约束）。
4. 首批真实 run 落地 → 运行证据积累 → P3 梯度按 §1.5 五要素逐档开放。
5. （远期条件触发）若未来真出现无人值守 A 轨需求，按 §5.2 清单启动 B#27 备选立项书，届时 DSH 才重新进入评估。
