### 4.3 责任主体机制化方案（合同 §4.4-3）

**证明合同**：每个自动动作可回溯到「哪个人的哪次签核」。数据面盘点（全部实测在表）：

| 链节 | 载体 | 责任语义 |
|---|---|---|
| 批准（责任锚） | `automation_approvals.requested_by_user_id` + `reviewed_by_user_id`/`reviewed_at`/`decision_reason` | 人签五要素：谁发起、谁批准、何时批、批什么（`arguments_sha256` 绑定）、何时执行（`executed_at`）；`risk_level/capability/tool_name` 定权限面。工作流 human_approval 节点（executor:1195+）与 DSH 审批回调同表落行 |
| 发起 | `workflow_runs.initiated_by_user_id` / `agent_runs` / `ai_call_audits`（ai_actor_id=提交人，goal-d14 finally 复位） | 每次自动执行有实名发起人 |
| 验收分离 | `gates.submitted_by_user_id ≠ decided_by_user_id`（403 gate_decider_conflict，dispatch_p0:249 钉）；ontology `change_sets` 拍板人≠提交人（403，ontology/service:24） | 执行人与拍板人强制分权 |
| 全事件落人 | `operation_events.actor_user_id` 非空（活库 44 事件/3 actor 全实名） | 每条状态变更可归人 |
| 系统自主动作=封闭白名单 | ①审批过期清扫（T-P1-5 原语 `_expire_approval`，翻转的 expires_at 是人工签发时设定）；②job 重试退避（RECOVERABLE 白名单，外副作用类型首败即终）；③outbox 投递；④bridge 4h 只读采集 | 四类全部有独立文档锚，均不触碰写类 external；责任锚=启用机制的人工配置/部署留痕 |

**结论：现有表够，无结构性缺口。**证明方式=①本核对表（32 例断言面）+②专项负向断言（S-5 绑定/过期、S-8 发布四闸、D-2 五道闸既有）+③活库可跑回溯 SQL（`automation_approvals` JOIN users 双侧人签非空，首批生产行落地即可执行）。待补的只有**运行证据**（误判率/审批时效取数口径=automation_approvals.requested→reviewed→executed 时延与 result_json，§0 实测现无生产行）——这正是 §4.4-2 把「附运行数据要求」写进评估报告轮的原因，不是闸的缺口。
