### 2.2 归因规则

| 来源 | 置信度 | 说明 |
|---|---|---|
| 硬性失败（HF-*） | **confirmed** | 硬性失败直接命中失败分类，证据即 HF 的证据 |
| 低分判据 **有证据** | **confirmed** | 判据直接对应分类，且带证据引用 |
| 低分判据 **无证据** | hypothesis | 仅分类相符 ⇒ 进人工复核队列，**不得**自动变提案 |
| 工具异常 | likely | 指向执行面（接口/权限），不指向访谈/方案能力 |

**只有 `confirmed` 根因能生成改进提案**——生成时若全部根因都不是 confirmed ⇒ **409**（把猜测当结论是改进系统最典型的失效方式）。

### 2.3 「只提案不落地」的四处强制落点

| 落点 | 实现 |
|---|---|
| 数据层 | 提案表**无** `published_at` / `publish_status` / `applied_at` / `apply_status` 等列；CHECK 只允许 `draft/in_review/approved/rejected` |
| 服务层 | 服务模块**无** `publish` / `apply` / `release` / `deploy` 类函数（AST 静态钉） |
| 跨域 | **生产模块（`fde_api` 下除 `simulation` 外）对改进提案零引用**（源码扫描静态钉） |
| 审批 | 审批需 project_lead/admin + **当前账号密码确认** + **理由必填**；审批**不等于**发布 |

`target_json` 只是**文本指针**（`kind` + `ref`），落地由人工在 V3.1 的治理面实施——V3.2 **不碰**任何生产 Prompt/Skill/Workflow/本体。

### 7.1 本轮修掉的两处设计缺陷

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| 1 | **「该有而没有」没有证据 ⇒ 永远不可核实** | 覆盖类判据（D1-01 等）零命中时 `evidence_refs` 为空 ⇒ 判据 `unverified` ⇒ 结论停在 `inconclusive` ⇒ **失败分析根本无从下手**（低分但无证据 ⇒ hypothesis ⇒ 不得生成提案） | 覆盖类判据的证据改为**双向**：命中项 + `expected_missing`（应命中却缺失的项）。「交付里没有 X」本身成为可引用证据 |
| 2 | **JSON 列上建 btree 索引** | PG 的 `json` 类型无默认 btree 操作符类 ⇒ 迁移执行期报错 | 删掉该索引；`target_kind` 过滤改在服务层做（与既有面同款） |

### 7.2 全量轮次的中断说明（如实记账）

G4 的全量 pytest 轮次在 48% 处被我**主动中止**：原因是 G5 的迁移与 `HEAD_REVISION` 改动在轮次运行**中途**落盘，会让该轮次的 revision 计数断言读到「新文件、旧断言」的混合态 ⇒ 必然假红。中止后统一在 G4+G5 完成后重跑全量（见 §7 表首行）。

> 教训：全量回归轮次**必须**在代码冻结后跑；边跑边改代码得到的红/绿都不可信。

## 11. 下一轮目标（G6 回归与盲测系统）

1. **数据集三分落地**：把 18 个案例按 `train/regression/blind` 分配并**物理隔离**（场景副本 + 装载分叉；盲测集的参考答案对被测方不可达）。
2. **回归套件**：套件 = 一组案例 + 一组运行；基线 vs 候选并排跑。
3. **对比报告**：逐维度 Δ、硬性失败集合差异、成本/时长差、**泛化差**（`gain_train − gain_blind > 0.15` ⇒ 过拟合风险）。
4. **新错误检测**：新出现的失败现象 / 新硬性失败 / 权限事件 Δ。
5. **过拟合闸**：过拟合 ⇒ 提案不得进入发布审批。

## 附录 · 诚实边界

- **改进提案的「改进对象」目前只是文本指针**——V3.2 **不实现**任何 Prompt/Skill/Workflow 的自动改写（设计如此：P8）。
- 十类失败分类与默认根因是**我方独立设计**的初版，映射关系（判据→分类）可被后续实测校准。
- 归因的置信度依赖评估判据的证据质量——若 L-A 判据本身判错，归因会跟着错。这是**单层依赖**，已在 §7.1 记录并改进（双向证据）。
- 本轮**未**实现回归与盲测——G6 的范围；未用占位数据冒充。
