## 0. 本轮开工前必须先解决的四个歧义（阻塞项）

这四项不是实现细节，是**命名与语义冲突**。开工前必须先出裁决文档，否则后续每个任务都会踩。

### 0.1 歧义一：现有 `level` 字段的 L1–L4 与角色分层同名不同义

**实测事实（`server/src/fde_api/dispatch/models.py` + `profiles.py`）**：
- `fde_profiles.level` 的 CheckConstraint 是 `level IN ('L1','L2','L3','L4')`，NULL＝未定级。
- `dispatch/profiles.py` 的 `LEVELS = ("L1","L2","L3","L4")`，`_DELIVERY_COUNTS = {"L1":1,"L2":3,"L3":8,"L4":15}`。
- 晋级判据是**交付能力事实**：独立交付单数、客户复购、带教人数、L4 要求全额收款；四域分数（biz_cognition / scenario_eng / ai_tech / delivery_assure）只用于评级评定。
- `dispatch/matching.py:59`、`scoring.py:18 LEVEL_RANKS`、`delivery_packages.required_level` 全部依赖它；`system_configuration.py` 的 `level_score_map` 映射 L1–L4 → 40/60/80/100。

**冲突**：本文档拍板的口径是**角色分层**——原文编号 L0 候选交付者、L1 独立 FDE、L2 实战营、L3 陪跑营、L4 区域合作商，且 Q08 已把 L0/L1 合并为「交付者」一身份两状态、Q24 定为「系统用四身份、对外保留 L 编号并维护映射表」。**角色分层与交付能力等级是两个正交维度，不能共用 `level` 字段**；且本仓库另有两处 L 编号占用，详见 §0.4。

**必须先出裁决**（ADR 格式，写入 `docs/commercialization/decisions/`）：
1. 现有 `fde_profiles.level` 保持**交付能力等级**语义，**不改名、不改值域**（它已被撮合、席位份额、评分全链依赖，改动面极大且会破坏既有测试）。
2. 角色分层另立字段（建议 `user_role`，值域 **R1 企业／R2 创业者／R3 交付者／R4 区域合作商**），**不复用 `level`，不落 L 编号**。
3. 对外 L 编号（L0–L4）作为**展示层映射**，由映射表从角色 + 订阅/认证状态推导，**不落为第二套权威值域**。
4. 裁决文档必须列出全部依赖 `level` 的代码位置与既有测试影响面。

### 0.2 歧义二：Q04 要求的四个权益字段在代码中完全不存在

**实测事实**：`training_entitlement` / `subscription_entitlement` / `certification_status` / `delivery_eligibility` 四者在 `server/src` 全库**零命中**（grep 无结果）。而「派单资格」的既有承担者是 `fde_profiles.status`（pending/active/suspended）+ `is_active`。

**裁决要求**：
- 四个字段**必须新增**，因为 Q04 拍板「权益须分四类字段管理，不得只用一个会员等级字段代表所有权益」，且这四类语义互不等价（培训权益、订阅权益、认证状态、交付资格）。
- **但 `delivery_eligibility` 不得覆盖或替换 `fde_profiles.status`**：后者是供给池生命周期（pending 不占名额→active 参与匹配→suspended），语义是「是否进撮合池」；新字段语义是「是否有资格接单并激活年度席位」。两者**并存**，并在 ADR 中写明各自判据与同步关系（例如：激活席位→status 由 pending 转 active）。
- `certification_status` 与 `fde_level_evidence` 的等级核验链并存：`certification_status` 是**是否已获认证**（培训出口），等级证据链是**能力等级评定**（派单内），二者不互相替代。

### 0.3 歧义三：T-13 分账结算与既有 `dispatch/settlements.py` 的边界

**实测事实**：`dispatch/settlements.py` 已有 `seat_shares_for(session, package)`（四席位份额实算）、`delivery_settlements` 表（r2 建）、`dispatch_rule_versions`（权重唯一来源＝版本表）、`disputes`（争议处理）。这些是**项目级派单结算**，已通过派单引擎 r1–r11 闭环并有 85% 覆盖率。

**裁决要求**：
- T-13 的「培训费、席位费、项目分成分别记账」是**收入科目分离**，与项目级派单分账**不是同一层**。禁止在 `delivery_settlements` 上加列硬塞；应新增**科目层**（收入类型 → 金额 → 关联订单/席位/分成事件），并通过外键指回既有结算与报价/合同对象。
- 项目分成的**比例**本次不定数（Q11 拍板「按角色与项目类型配置」），故本期只落**科目与配置结构**，不落具体比例常量。
- 席位份额计算**继续复用** `seat_shares_for`，不得另起一套。

### 0.4 歧义四：L 编号四套同名不同义 —— 角色分层改用 R1–R4

**实测事实（四套 L，全部已存在且互不相干；方向亦不同）**：

| L0–L4／L0–L5 | **角色分层**（BP §7.10 五层角色，原文商业口径） | 组织轴 | 待新增 | — | 与上述三者冲突 |

**裁决要求（已拍板，2026-11-08 第六批）**：
1. **系统内角色分层一律用 R1–R4**：R1 企业／R2 创业者／R3 交付者／R4 区域合作商。**不落 L 编号**。
2. **既有的三套 L 都不改**——字段名、值域、语义全部保持不变。`fde_profiles.level` 被撮合／评分／包要求等级／系统配置全链依赖，改名或改值域会打爆既有测试；`fallback_level` 是 Agent 降级链既有契约；智能化等级是 BP 文档口径。**处置方式是在代码注释与文档中加区分说明，不改代码。**
3. **对外 L0–L4 商业编号仅存于映射表**，从角色＋订阅／认证状态推导；映射表是唯一转换入口，**代码中不得散落 L 编号换算**。
4. 原文「L2 实战营 9800／L3 陪跑营 19800」的 L 编号是**培训营档位**，与上述四者均无关；代码与文档中统一称「实战营」「陪跑营」，不用 L 编号指代。
5. **刻度方向必须显式标注**：智能化等级越大越自动化，交付能力等级越大越资深，**降级等级越大越不自动化**——三者方向不一致，任何一处引用都须写明是哪一套。
6. ADR-001 必须列出全部依赖 `level` 的代码位置与既有测试影响面，并写明与 `fallback_level`、智能化等级的区分。

### 0.5 本轮基线事实：系统交付智能化等级 L2+（向 L3 演进中）

**权威分级框架（BP v4.0 §1.3a「交付智能化等级 L1–L5」）**：参照业界自动化/智能化通行分级法，**数字越大越自动化**，与自动驾驶分级同义：

| 等级 | 名称 | 定义（判定标准） |
| --- | --- | --- |
| L1 | 人工交付 | 全部工作由人完成，系统仅记录与存储 |
| L2 | 流程自动化 | 规则驱动的流程引擎承担主线（报价、收款节点、合同窗口、门禁校验、状态机由系统强制执行）；人做判断与执行 |
| **L3** | **AI 辅助交付** | 在 L2 之上，AI 生成初稿物（方案、报价、诊断报告、代码脚手架），**人工审核修改后交付**；AI 参与派单推荐 |
| L4 | 监督自主 | AI 端到端完成标准单的全节点交付（含证据链），人只做异常处理、终审与客户沟通 |
| L5 | 全自主交付 | 标准单全程无人介入；理论上限 |

**当前评级（书面权威口径，BP v4.0／官网 llms.txt／文档总览三处一致）**：**L2+（强 L2，向 L3 演进中）**——报价引擎、里程碑收款、合同验收窗口、门禁 G1–G9 证据链、SOP 状态机、派单撮合规则引擎已上线（L2 证据）；AI 智能体已承担方案初稿、诊断报告草拟、文档整理（已触及 L3）；**交付主体仍是人工执行，平台工程师终审与兜底是质量主承重，AI 生成物必须过人工审核才能出门禁**。

**业务方判断（2026-11-08 口述）**：系统自动化程度**目前约 L3**。本任务书采信此判断作为设计前提，但**评级升格需按 BP §1.3a 的证据口径走，不得据口述直接宣称已达 L3**。

**⚠ 与 `agent_runs.fallback_level` 的区分（易混，必读）**：`fallback_level`（L0–L3）是**单次 Agent 运行的降级去向**，刻度方向**相反**（L0 正常 → L1 模型直连 → L2 模板填空 → L3 人工接管，数字越大越不自动化）。它**不是**智能化等级，不得用其数值推断系统自动化水平。

**对设计的三条硬约束**（依据是 L3 的定义本身——「AI 出初稿、人审核后交付」，而非"系统不能自动做"）：
1. **关键流转默认需人工确认**：免费诊断确认、额度扣减、席位激活、商机归属确认、区域升级——AI 可生成草稿与建议，**不得自动判定即生效**。这是 L3 的固有形态（人从「写」变成「审」），不是能力缺失。
2. **企业自助三档分流是人工判定，不是系统自动分级**（与 G6 拍板口径一致：三档定性判据由交付咨询环节人工判定并留痕，不做系统硬规则）。L3 下系统可出分流建议，但分级判据本身是业务判断，判定权在交付咨询环节。
3. **「完成判据」与「触发时点」必须可被人工中断与接管**，且人工接管路径须留审计事件（与既有 `handoff_run` 的 `handoff_user_id` + signoff checkpoint 模式一致，不建第二套）。

**须在 G0 基线审计中实测校准**：AI 草稿的**采纳率**（人工接受/修改/拒绝分布）、`handoff_user_id` 人工接管频次、Gate 人工审核通过率、`fallback_level` 分布（仅作降级链现状，非智能化等级）——用**实测数据**替代口述判断，作为 G2–G6 设计强度的依据。**不得在未取得实测数据前声称系统智能化等级已达 L3。**

## 1. 总体决策

### 1.1 商业化双业务线目标闭环

```
企业注册（免费） → 一次完整业务诊断 → 系统呈现三选项 → 付费路径
                                        ↘ 商机归属（创业者报备/平台确认/保护期）
交付者免费注册 → 申请认证 → 候选池 → 首个付费项目交付完成并验收 → 激活 3980 年度席位 → 接单分成
创业者免费体验 → 实战营 9800 / 陪跑营 19800（均含首年席位）→ 认证 → 正式运营
区域：城市观察伙伴（免费申请）→ 城市服务伙伴（按项目结算）→ 正式区域合作商（29800 起）
                                                        ↑ 闸门：首次对外收费签约前
```

### 1.2 设计原则

1. **两条业务线分开定价、分开转化，共用同一套交付系统**——企业自助不得被迫成为学员或代理商。
2. **免费边界即产品边界**：免费只到一次完整业务诊断报告；不含实施、真实系统接入、大规模数据处理、定制 Agent、生产部署、持续运维与驻场。
3. **额度按主体计，不按账号计**：企业免费额度按企业主体认定、一次一主体、长期有效不重置。
4. **权益四分**：培训权益／订阅权益／认证状态／交付资格分别建模；「套餐已含席位则不重复收取」是硬规则。
5. **扣费前置**：交付者首单扣费在**交付完成并验收后**触发，且须事先书面选定方案。
6. **规则先立框架、数值后填**：商机保护期、分成比例、陪跑期限、模拟体验上限等均先建可配置结构，数值待试点数据。
7. **未签约即不收费**：区域合作商模块售卖能力默认关闭，开关条件绑定合规条件清单已签署——做成系统约束，不靠人记着。
8. **事实源在数据库**：权益、额度、归属、席位、科目均落库可查；关键写操作留审计事件。
9. **复用优先**：既有 `dispatch` 模块（撮合、席位、结算、档案、等级）**扩展而非重建**。
10. **命名避让**：系统内角色分层用 R1–R4，**不落 L 编号**；既有三套 L（智能化等级 L1–L5、交付能力等级 `fde_profiles.level` L1–L4、自动化降级等级 `agent_runs.fallback_level` L0–L3）语义与**刻度方向**均不同，**一律不改**（§0.4）。
11. **按 L3「AI 出初稿、人审核后交付」设计**：当前交付智能化等级 L2+（向 L3 演进），关键流转**默认需人工确认**，AI 产出走草稿／审核区；人工接管路径须留审计事件（§0.5）。

### 1.3 明确不做

- 不推倒重写 `dispatch` 模块，不建第二套撮合、席位或结算引擎。
- 不修改 `fde_profiles.level` 的既有值域与语义（见 §0.1）。
- 不在本期落具体分成比例、认证费金额、陪跑期数值、模拟体验上限值、项目等级金额区间——这些按拍板结论「本次不定数」。
- 不实现区域合同的对外签订能力（T-12b）——本期只做 T-12a 能力建设。
- 不做「企业完全自助」的对外承诺（T-16 为 P2 后续）。
- 不改动 V3.1 在跑的 P0/P1 线（Agent/Workflow/Ontology/访谈/Gate/证据）任何业务代码；与本线的交叠只允许走 §3 的接口层。
- **不做「系统自动判定即生效」的关键流转**——交付智能化等级 L2+（向 L3 演进），L3 的定义即「AI 出初稿、人审核后交付」，关键流转默认人工确认（§0.5）。
- 不改动 `fde_profiles.level` 与 `agent_runs.fallback_level` 的字段名、值域或语义（§0.4）。
- 不引入新的付费模型或 SaaS，优先复用现有 AI Server、模型配置与工具体系。
- 不执行生产变更、不对客户发送消息、不删除用户数据、不读取无关密钥。

## 5. G1：权益四分与角色分层（对应 T-04、T-05）

### 目标
把「四类权益分字段管理」与「系统四身份、对外保留 L 编号」从文档变成可校验的数据库与服务语义。

### 数据模型（目标语义，须先核验再落）
- **角色字段**：**优先 `users` 表加列**（若 `users` 已有角色列则复用并扩展值域），值域**四值 R1–R4**：`R1` 企业／`R2` 创业者／`R3` 交付者／`R4` 区域合作商。**不得使用 L 编号**（§0.4）。
- **对外编号映射**：另建映射（角色＋订阅／认证状态 → 对外 L0–L4 商业编号），**映射表是唯一转换入口**，代码中不得散落换算。
- 四类权益**独立建模**（表或字段组，ADR 定），语义分别：
  - 培训权益：购买与有效期（培训费、认证费、陪跑）
  - 订阅权益：年度席位（3980）、激活状态、激活来源、到期
  - 认证状态：未认证／已认证（挂模拟考核结果）
  - 交付资格：是否具备接单并激活席位资格
- **不覆盖 `fde_profiles.status`**（§0.2），并在同库内建二者关系说明。

### 约束
- 四类权益任一不得由其他推导替代；禁止用单一「会员等级」字段表达全部。
- **不修改** `fde_profiles.level`（L1–L4 交付能力等级）与 `agent_runs.fallback_level`（L0–L3 自动化降级等级）的字段名、值域或语义；**不得新增任何以 L 开头的角色枚举值**。
- 「套餐已含首年席位则不重复收取」落为**可测的不变量**（实战营 9800 与陪跑营 19800 均含首年 3980）。
- 权益变更须留审计事件（Actor、对象、前后状态、时间、来源、请求 ID）。
- **权益变更、额度扣减、席位激活属高风险写，默认需人工确认**（交付智能化等级 L2+／L3 形态：AI 出草稿、人审核后生效，§0.5）；人工确认路径须留审计事件，且可被人工中断与接管。

### 验收
- 四类权益字段/表齐备且互不覆盖；`fde_profiles.level` 与 `agent_runs.fallback_level` 值域与既有测试**零改动通过**。
- 角色枚举值域为 R1–R4，**代码与迁移中不出现以 L 开头的角色值**。
- 至少 3 条反例用例证明「单一会员等级字段」方案被拒（不得用放宽断言蒙混）。
- 迁移有升级与兼容测试。

## 6. G2：免费额度与三个体验入口（对应 T-07）

### 目标
免费只到一次完整业务诊断，且额度按企业主体计。

### 语义
- **企业主体判定**：一次一主体、长期有效不重置。主体认定键（工商口径）**须先出 ADR** 并提示法务确认；多子公司是否分别体验须显式规则（本期先给保守默认：不分别）。
- **诊断完成判据**：六项免费交付物全部产出并经企业确认（企业问题诊断报告、业务流程初步分析、AI 应用机会清单、建议实施方案、预计项目等级与预算区间、下一步实施建议）。
- **项目等级与预算区间**：三档描述性表述，**不给数值区间**，与区域席位档 T1–T3 解耦。
- **三入口隔离**：企业＝真实业务问题；创业者＝模拟体验；交付者＝脱敏模拟项目考核。
- **使用限制**：创业／交付两档算力与人工指导上限各一个数值；**禁止无上限**（本期先落可配置结构 + 保守缺省值，标注「试点前须填实数」）。
- **不免费范围**须在代码层与文档层同时可见：完整实施、真实 CRM/ERP 接入、大规模数据处理、定制 Agent、生产部署、持续运维与驻场。

### 验收
- 换账号不重置额度（同一主体再注册不得获得第二次）。
- 六项交付物未齐备不算完成；六项不免费内容不进入免费流程。
- 创业者不能取到企业真实商机；交付者触及上限即受限。
- 至少 1 条变异用例证明「额度按账号计」的实现会转红。

## 7. G3：订阅、培训与科目结算（对应 T-10、T-11、T-13）

### 目标
把席位、培训、认证、陪跑与收入科目分离落库。

### 语义
- **首单激活**：交付者首个付费项目**交付完成并验收后**触发扣除 3980；扣费方式方案 A（一次性扣除）为默认，**须交付者事先书面选定**；未接单候选人不产生年度欠费。
- **席位不重复收**：L2 9800、L3 19800 均含首年 3980；L0 首单扣费仅适用于未购其他含席位套餐者。
- **认证独立收费项**：认证费作为独立收费项存在，**金额本期不设**（留配置位，缺省不可收款）。
- **认证挂模拟考核**：认证状态由模拟考核结果驱动；**通过线本期不设**。
- **陪跑期限与培训周期挂钩**：结构先落，数值待定。
- **科目层**：培训费、席位费、项目分成分别记账可分别核对；软件订阅／企业订阅／使用量／项目费／软件服务费／平台分成六项名目只定义归属，**不定义计算方式**（结账金额本期走线下约定）。
- **分成比例本期不定数**：只落「按角色与项目类型配置」的结构。

### 约束
- 席位份额计算**复用** `dispatch/settlements.py::seat_shares_for`，不另起算法。
- 不得在 `delivery_settlements` 上加列硬塞科目（§0.3）。

### 验收
- 「套餐含席位不重复收」有反例用例（含 L2／L3／L0 三种组合）。
- 首单扣费在验收前不触发；未选定方案时不得扣费。
- 三类科目分别可查、可对账。
- 新增服务端逻辑有测试；新增路由有权限测试。

## 8. G4：商机归属与渠道保护（对应 T-09）

### 目标
立「报备→确认→保护→撮合→结算」链路，且**规则数值本期不定数**。

### 语义
- 七步链路完整：创业者提交企业线索 → 企业确认有真实需求 → 平台确认商机归属 → 设定保护期 → 创业者负责售前与客户关系 → 平台撮合交付者 → 按既定分成规则结算。
- 已确认归属的商机，**企业后续直接注册不得简单转移**给其他人。
- 保护期、续期条件、客户自主选择权、争议处理机制**写入成文规则**；规则数值（保护期长度、续期条件、归属判定）**本期不定数**——须以**可配置结构**落地，成文前以配置态留空或临时规则兜底，**不留硬编码默认值**。
- 商机保护**不得变成永久锁定企业**。

### 验收
- 归属确认后企业自行注册，商机不自动易主（至少 1 条反例）。
- 保护期为空时行为是「未配置」而非「永久保护」或「立即失效」，且两者可区分。
- 规则文件与代码中的配置位一一对应。

## 9. G5：区域合作商能力建设（对应 T-12a，**不含 T-12b**）

### 目标
建区域阶梯的**内部能力**，同时**不具备**对外收费签约能力。

- **售卖能力默认关闭**：区域合作商模块不得具备对外收费签约能力；须有显式开关，开关开启条件绑定「合规条件清单已签署」。

### 硬约束（合规）
本期**不做** T-12b。以下为**放行前必须齐备**的条件清单（来自《商业特许经营管理条例》第七、八、十二、二十一条及《商业特许经营信息披露管理办法》第四条），本期只登记为开关条件，**不实现任何收费签约路径**：
1. 首次订立特许经营合同后 15 日内向商务主管部门备案；
2. 订立合同**之日前至少 30 日**书面披露经营资源、费用构成与合同文本；

### 验收

## 10. G6：企业空间与企业自助交付（对应 T-06、T-08）
